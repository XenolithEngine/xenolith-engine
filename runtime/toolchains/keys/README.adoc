# Pinned OpenPGP release keys

The public keys the source fetcher checks upstream release signatures against.
One file per signer, ASCII-armored and exported minimally (no third-party
certifications), so a change to any of them is legible in a diff.

`src.mk` points a dependency at a key with `<name>_KEY`, and the fetcher
(`common/utils/fetch.sh`, `fetch.ps1`) verifies the detached signature named by
`<name>_SIG` against `keys/<name>_KEY.asc` in a throwaway keyring. Nothing here
is imported into the user's own GnuPG keyring, and no keyserver is contacted at
build time - if a signature does not verify against the file committed here, the
download is refused.

## What actually protects a build

Two layers, and it is worth being clear about which does what:

* **The pinned `_SHA256` in `src.mk` is the load-bearing check.** The expected
  value lives in our git history, so an everyday `make download` is verified
  against something the upstream server cannot change.
* **The signature check protects the moment a pin is written.** A hash pin is
  only as good as the download it was computed from; verifying the signature is
  how you establish that download was genuinely upstream's before recording its
  hash. So a version bump should be done on a host with `gpg` installed.

Because of that split, a missing `gpg` is a warning rather than an error by
default. Set `SP_REQUIRE_SIGNATURES=1` to make it - along with an unsigned
source or a missing key file - a hard failure:

[source,sh]
----
# From runtime/toolchains
make download SP_REQUIRE_SIGNATURES=1
----

Fourteen of the archive dependencies are signed upstream. The rest pin a
SHA-256 only; each such block in `src.mk` says so and why. Dependencies fetched
with git are pinned by commit instead, which is the same idea by other means.

## Where each fingerprint was confirmed

A key taken from a keyserver is trust-on-first-use: keyservers accept uploads
from anyone. Eleven of the fourteen were therefore re-fetched from a location
the project itself controls and compared fingerprint-for-fingerprint.

The remaining three - **zstd**, **libwebp** and **freetype** - publish no key
anywhere we could reach that is separate from the signature itself, so they came
from a keyserver. What is checkable about them is continuity: the same key has
signed years of prior releases, which an attacker who had merely uploaded a
lookalike key to a keyserver could not arrange.

* `zstd.asc` also verifies zstd 1.5.6 and 1.5.0.
* `libwebp.asc` also verifies libwebp 1.5.0, 1.2.0 and 1.0.0 - back to 2018.
* `freetype.asc` also verifies FreeType 2.13.3 and 2.12.1. It does *not* verify
  2.11.0, which predates a key rotation.

If you can confirm any of these three against a project-controlled source,
replace the row above with it.

## Adding or rotating a key

A signature that stops verifying is either an upstream key rotation or an
attack, and the two look identical from here. Do not update a key because a
build failed; update it because you checked.

. Find the fingerprint on a page the project controls - its own domain, its
  release documentation, or the account that publishes the releases. Not the
  keyserver, and not a link found on the page serving the tarball.
. Fetch the key and confirm the full fingerprint matches, character for
  character. A 64-bit key id is not sufficient.
. Export it minimally and commit it:
+
[source,sh]
----
gpg --armor --export-options export-minimal --export <fingerprint> > keys/<name>.asc
----
. Record where you confirmed it in the table above.
. Re-run the download for that dependency with `SP_REQUIRE_SIGNATURES=1` and
  update its `_SHA256` in `src.mk` from that verified download.
