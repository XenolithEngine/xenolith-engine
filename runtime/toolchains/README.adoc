# Xenolith Toolchains repository

The purpose of this repository is to provide universal complete toolchain for C/C++ development with Xenolith Runtime on MacOS, Windows and Linux.

**Work in progress**: toolchains on beta stage now. It works, compiles and mostly tested.

## Hardware requirements

At least 32G RAM and 100G disk space required for full build (all hosts + all targets).

Most heavy host toolchains is windows, if it compiles - all other will not OOM too.

Release toolchains assembled on x86_64 linux, other platform were not tested for full builds.

Note: Apple hardware is required due licensing limitations to build apple hosts and targets.

## Build steps

### Download sources

Download dependencies to build

[source,sh]
----
# From runtime/toolchains
make download
----

Every download is checked before it is allowed into `src/`: the transfer has to
succeed, the archive has to match the SHA-256 pinned in `src.mk`, and the
fourteen dependencies whose upstreams publish a detached OpenPGP signature are
verified against the keys committed in `keys/`. Anything that fails stops the
build instead of leaving a partial tree behind. Sources fetched with git are
pinned by commit, so a moved tag is refused too.

Install `gpg` to get the signature checks; without it they are skipped with a
warning and the SHA-256 pins still apply. For release and CI builds, make that
skip an error:

[source,sh]
----
# From runtime/toolchains
make download SP_REQUIRE_SIGNATURES=1
----

See `keys/README.adoc` for the key fingerprints, where each was confirmed, and
what to do when one stops verifying.

### Build host toolchain

See README.md in host-* directory for concrete steps performed and prerequisites.

[source,sh]
----
# From runtime/toolchains
make host
----

----

* target-aarch64-unknown-linux-gnu
* target-riscv64-unknown-linux-gnu
* target-loongarch64-unknown-linux-gnu
* target-x86_64-unknown-linux-musl
* target-aarch64-unknown-linux-musl
* target-riscv64-unknown-linux-musl
* target-loongarch64-unknown-linux-musl
* target-unknown-ndk-linux-android - special target to use with Android NDK
* target-aarch64-unknown-linux-android
* target-armv7a-unknown-linux-androideabi
* target-i686-unknown-linux-android
* target-x86_64-unknown-linux-android
* target-x86_64-apple-macosx
* target-aarch64-apple-macosx
* target-aarch64-apple-ios
* target-x86_64-apple-ios-simulator
* target-aarch64-apple-ios-simulator
* target-x86_64-pc-windows-msvc
* target-aarch64-pc-windows-msvc

The Apple targets (`*-apple-macosx`, `*-apple-ios`, `*-apple-ios-simulator`) need
the matching Apple SDKs. On a macOS host they are located automatically through
`xcrun`. When cross-building from a non-Darwin host they must be provided under
`src/` as `MacOSX.sdk`, `iPhoneOS.sdk` and `iPhoneSimulator.sdk` (these are not
fetched by `make download` — they are extracted from Xcode / the Command Line
Tools and are subject to the Apple SDK license). The deployment targets are
`SP_MACOS_VER` / `SP_IOS_VER` in `target-apple/Makefile`. There are three iOS
sysroots: `target-aarch64-apple-ios` (device) plus the
`target-{x86_64,aarch64}-apple-ios-simulator` simulators; `make target-ios`
builds all three. On iOS the Vulkan validation layer is shipped as
`VkLayer_khronos_validation.framework` (upstream forces a framework there)
instead of a flat `.dylib`.

### Build cross host toolchains

Besides the native host toolchain (`make host`, built with a multi-stage
bootstrap for the build machine), additional host toolchains for *other*
platforms (or a simplified rebuild for the same one) can be produced by
*cross-compiling* them with the already-built native host's clang.

The overall build order is:

1. Build **one** native host toolchain for the build machine — `make host`.
   This is the only toolchain produced by a full bootstrap.
2. Build the **targets** — `make target-<triple>`. Each target sysroot already
   contains a complete libc of the required version (glibc/musl), libc++ and
   compiler-rt.
3. Build the **cross host toolchains** *from the targets* (where necessary) —
   `make host-cross-<triple>`. The cross host build reuses the native host's
   clang as the cross-compiler and, where the libc cannot be produced by clang
   alone (glibc needs GCC), the pre-built libc sysroot of the corresponding
   target. Therefore each `host-cross-*` recipe depends on the matching
   `target-*` in this Makefile.

[source,sh]
----
# From runtime/toolchains, after `make host` and the relevant `make target-...`
make host-cross-x86_64-unknown-linux-gnu     # reuses target-x86_64-unknown-linux-gnu glibc
make host-cross-x86_64-unknown-linux-musl     # musl libc is built inline (no target needed)
make host-cross-x86_64-pc-windows-msvc        # reuses the Windows SDK (xwin)
make host-cross-x86_64-apple-macosx           # reuses the macOS SDK
----

Supported cross hosts: `host-cross-{x86_64,aarch64,riscv64,loongarch64}-unknown-linux-{gnu,musl}`,
`host-cross-{x86_64,aarch64}-pc-windows-msvc`, `host-cross-{x86_64,aarch64}-apple-macosx`.
See the `cross/` subdirectory and `README.adoc` of each `host-*` directory.

## Sources list policy

The list of sources for source codes must be updated regularly. After the build of a new version is confirmed, the date of its update is placed next to the corresponding source in the format `revised: 22 feb 2026`.

Official sources are used, however, for sources whose access is restricted based on download region, an alternative method should be used (for example, direct download from the repository).

Each entry in `src.mk` carries what it is verified by. Bumping a version means
updating that too, on a host with `gpg` installed:

* an archive gets a `_SHA256`, computed from a download whose signature you have
  just verified - not copied from a checksum the same server published;
* a git source gets a `_COMMIT` next to its `_TAG`. `make src-pins` re-resolves
  every tag to the commit it points at today. A line that comes back changed for
  a tag nobody touched means upstream re-tagged, which is worth understanding
  before the pin is updated;
* a source with no signature says so in its block, and why that is acceptable.

Verification failures are not build breakage to route around. A SHA-256 mismatch
or a bad signature is the check doing its job; find out why before changing a pin.

ENGINE support for the GOST engine. The Brotli, zlib, libpng, FreeType, HarfBuzz,

Expat's `replacements/expat/2.10.0-security/` series backports
https://github.com/libexpat/libexpat/pull/1492[upstream PR #1492]

`3d77567612994172f9d09b46f31bb604e16fb08d`). This closes an overread in custom
encoding diagnostics, scheduled upstream for 2.11.0. The matching regression
fails against stock 2.10.0 and passes with the backport. CVE-2026-128241 affects
the `xmlwf` tool, which the target recipe does not build.

Archives with detached signatures were verified using the keys already pinned
under `keys/`; unsigned archives have new SHA-256 pins and git sources have
both tag and commit pins in `src.mk`. The Brotli LoongArch and HarfBuzz e2k128
patches still apply. The Vulkan Loader Tau patch changes context only for the
new loader release. zlib's installed static archive keeps the consumer name
`z.lib` / `libz.a`, including correct installed CMake exports. FreeType keeps
static HarfBuzz integration (with an FT-free HarfBuzz bootstrap for an empty
sysroot), and WAMR reuses the SIMDe source pin instead of fetching another copy.

The direct third-party harness now checks SQLite transactions/JSON, Brotli
round trips and truncated input, Expat malformed UTF-16 and custom-decoder bounds, libffi mixed argument
calling conventions, and the OpenSSL empty-AAD / invalid-IV security regressions.
The Expat/libffi checks are Linux-only because those libraries are not shipped
in the Windows target.

compiler, system libraries and vendor SDKs. Local exports are under
`runtime/toolchains/targets/`; the isolated build trees are under
`runtime/toolchains/intermediate/refresh-20261116/`. These are local build
artifacts, not a signed SDK release or a replacement of the configured SDK.

All 29 exports passed architecture inspection (1218 static/import archives).
Version checks passed for 189 dependency headers; the 30 existing C++/runtime
archives and 226 compiler-rt archives compared with the installed SDK stayed
byte-identical. The `+dll` exports carry the rebuilt current sprt DLL and its
import library. glslang and SPIRV-Tools from the new SDK were built separately
for the Linux host and used for the shader checks.

The compiler's 363 exported unwind, sanitizer, profiling and related headers
also match the original SDK; they are not part of the dependency overlay.

The direct dependency tests pass with network checks enabled: 284 checks on
Linux and 274 under Wine, including a verified HTTPS transfer and the local
TLS handshake. Upstream Brotli tests pass on both platforms (12/12 each).
The OpenSSL EC, QUIC-stream and QUIC state-machine suites pass on Linux.
Both tessellation goldens pass on Linux and under Wine without changing their
reference files; Vulkan compute runs real checks on both platforms. The libc
comparison gives identical output for all 78 common cases; the Windows-only
`io_msvc` case runs successfully on Windows and prints a skip on Linux.

`tests/run-checks.py -j4` passes all 12 selected jobs (22,828,860 checks).
The full Linux run executes 74 jobs and 130,188,037 checks. Ten UI jobs fail
under concurrent load; every one passes when repeated individually with
`full --only <check> -j1`. The initial full run is retained as a failed run,
not relabelled green. Three jobs are explicitly skipped: `tauwsitest` needs
the excluded Mesa/Tau headers, and `wgpucompute` / `flowwgpu` need a
`libwgpu_native.so` absent from the installed SDK.

The pre-commit full rerun at `-j2` executes 74 jobs and 130,188,333 checks,
with one failed job: `remote-render-check.py` captures four correct square
images in its three-second window but requires at least five. Its subsequent
standalone run passes all 15 checks, as does a separately built original-SDK
baseline. The failed full run remains recorded rather than labelled green.

The clean native-host export repair has another full run: 74 jobs,
130,188,302 checks and one `remote-multi-check.py` exception. Its standalone
rerun passes all 31 checks. The export itself is checked against the freshly
built libc++abi: explicit export targets depend on the stage build markers,
so GNU Make need not discover CMake's output files before they exist.

Windows runtime verification was also compared with the original installed SDK.
Both builds have the same failures: `libc_at` (`faccessat`/ENOTDIR),
`runtime_address_wait`, and timeouts in `runtime_dispatch` and `libc_setjmp`;
the other 52 runtime cases pass. Stappler's `ForceContainer` configuration cannot
exercise the suite under Wine, so the console validation uses
`APPCONFIG_APP_PATH_COMMON=0`. It runs 3208 successful checks and the same 13
failing assertions with either SDK: application-directory writes and invoking
the external Windows `unzip` program. These results are not reported as green
Windows suites and their runtime implementations are outside this refresh.

WebAssembly execution was checked with Node.js 24.22.1 and the repository's
`runtime/wasm-js/run-node.mjs` host, using clean builds against the refreshed
sysroots. Both wasm32 and wasm64 pass 257 direct dependency checks (including
the OpenSSL security regressions and an in-memory TLS handshake), 3191 Stappler
checks, and the bundled-file smoke test. All 56 runtime cases exit successfully
on each target, retaining their explicit platform skips (processes, sockets,
setjmp, Windows-only checks and unavailable locales; wasm64 probes also skip on
wasm32). Both libc runs execute 76 cases without traps and produce identical
output. The wasm64 high-memory test actually allocates above 4 GiB and verifies
memory operations, file reads, random bytes, thread stacks and mutexes there.
The optional external KDL suite is absent; loopback TCP and public HTTPS tests
are excluded because the wasm host has no socket backend. These are Node
console checks, not browser/WebGPU validation.

These runs found that curl's descriptor-based multi wakeup initialization fails
on the wasm libc and presents as an out-of-memory error, including with the
original SDK. The wasm curl recipe now disables socketpair wakeups; `file://`
transfers and the multi interface pass on both pointer widths. The feature test
also checks the synchronous resolver that this target explicitly configures.
The same harness still passes all 284 Linux and 274 Wine network checks.
The installed CLI does not register wasm64 as an available target, so its
builds use a maintenance project driven by the CLI, forwarding the explicit
wasm64 target and sysroot to the existing make recipes.

The local validation summary, raw logs and source/signature provenance are in
`runtime/toolchains/tmp/refresh-validation-20261116/`.

## Code style

Most of the build scripts here can be used both in the GNU environment and in PowerShell on Windows. For this purpose, standard commands (cp, rm, and others) are implemented as functions `rule_*`, which ensures their uniform behavior.
