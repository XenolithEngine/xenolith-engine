# Linux musl host toolchain build directory

Здесь собирается host-тулчейн (clang/lld + libc++ + llvm-инструменты + glslang/
spirv-tools) для работы *непосредственно на Linux с musl* (Alpine и подобные).

В отличие от glibc-хоста, не требуется собирать GCC и «двойную» libc: musl
самодостаточна и собирается любым современным компилятором, а на musl-Linux уже
есть системный clang, которым выполняется бутстрап. Поэтому здесь две стадии
вместо трёх.

== Источник musl

Используется *запиненная* по коммиту musl из репозитория — git-сабмодуль
`runtime/musl-libc` (версия 1.2.6, commit `5122f9f3...`). Сборка ведётся
out-of-tree (через `$(MUSL_SRC_DIR)/configure`), исходники сабмодуля не
модифицируются. Перед сборкой убедитесь, что сабмодуль выкачан:

[source,sh]
----
git submodule update --init runtime/musl-libc
----

== Prerequisites

Сборка выполняется на Linux/musl. Требуются:

* системный *clang* и *lld* (бутстрап-компилятор; см. `BOOTSTRAP_CC`/`BOOTSTRAP_CXX`)
* *build-base* (gcc/g++/musl-dev/binutils) — системный clang использует gcc-crt и
  libstdc++ при сборке бутстрап-бинаря clang
* *cmake* и *ninja* (samurai)
* *GNU make*, *git*
* *python3* (нужен compiler-rt), *rsync* (нужен `make headers_install` ядра)
* *linux-headers* (kernel headers для сборки host-инструментов LLVM)

На Alpine:

[source,sh]
----
apk add build-base clang lld cmake samurai make git python3 rsync linux-headers
----

NOTE: Собрано и проверено на Alpine 3.24.1 (musl 1.2.6, clang 22) внутри
bubblewrap-песочницы: stage0/stage1/out проходят, поставляемый тулчейн
компилирует и запускает C++ (STL+исключения) и проходит конвейер
glslang → spirv-link → spirv-val.

== Stage 0 (бутстрап)

Системным clang собираются:

. запиненная musl -> `sysroot-stage0` (наш C-рантайм и sysroot);
. рантаймы LLVM (compiler-rt, libunwind, libc++abi, libc++) под musl;
. clang + lld.

Полученный clang скомпилирован системным компилятором, но настроен на наш
musl-sysroot (`DEFAULT_SYSROOT`, default rtlib=compiler-rt, stdlib=libc++,
linker=lld, unwindlib=libunwind) и пригоден для сборки самодостаточного stage1.

== Stage 1 (финал, self-hosted)

Компилятором stage0 собирается финальный набор в `sysroot-out`:

. musl (заново, stage0-clang);
. shared-рантаймы (поставляются и используются для линковки финального clang);
. zlib и libxml2 (build-time зависимости clang/lldb, линкуются статически);
. финальный clang/lld/**lldb** + `libLLVM.so` с мульти-таргетным backend-ом
  (`X86;ARM;AArch64;RISCV;WebAssembly`) — чтобы хост-компилятор мог
  кросс-компилировать движок под все цели;
. spirv-tools и glslang (с `ENABLE_OPT`, нужны движку:
  `HOST_GLSLANG` / `HOST_SPIRV_LINK`);
. GNU make (host-овый `make` в составе тулчейна).

Итоговые бинарники слинкованы с нашим libc++ (rpath `$ORIGIN/../lib`), а
`PT_INTERP` указывает на стандартный `/lib/ld-musl-<arch>.so.1`, поэтому тулчейн
работает на любом musl-Linux.

zlib/libxml2 ставятся в отдельный чистый префикс (`build/stageout-extra-install`),
а spirv-tools — в свой (`build/stageout-spirv-install`); их include подключается
через `-isystem`. Это важно: добавление `-I<sysroot>/include` (с C-заголовками
musl) ломает порядок `#include_next` в libc++ при сборке C++-кода.

== Сборка

[source,sh]
----
# из runtime/toolchains
make download              # один раз: тянет llvm/zlib/glslang/... в ../src
git submodule update --init ../musl-libc

# автоопределение хоста (на musl-Linux выберется host-linux-musl)
make host

# либо напрямую:
make -C host-linux-musl out OUT_SYSROOT=$(pwd)/hosts/x86_64-unknown-linux-musl
----

== Cross-сборка (упрощённая, из любого Linux)

Подкаталог `cross/` собирает тот же musl-host, но *без двухстадийного
self-host бутстрапа* — по аналогии с `host-macos/cross` и
`host-windows-msvc/cross`. Используется уже собранный мульти-таргетный тулчейн
билд-машины (`hosts/<HOST_ID>`): его clang кросс-компилирует musl, рантаймы и
финальный clang/lld/lldb напрямую (`--target=<triple>-musl`). Один проход
вместо двух; собирать можно с любого Linux (glibc или musl), не только с musl.

[source,sh]
----
# из runtime/toolchains; сначала нужен host билд-машины (make host)
make host-cross-x86_64-unknown-linux-musl
make host-cross-aarch64-unknown-linux-musl
make host-cross-riscv64-unknown-linux-musl
----

Те же опции (`SP_LLVM_LTO`, по умолчанию здесь *выключен* для скорости),
shared-libc++ и раскладка, что и у нативной сборки. Курица/яйцо рантаймов (нет
готового libc++ для compiler-check) решается как в `target-linux/musl`
(`CMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY`) + форс
`LIBCXXABI_HAS_CXA_THREAD_ATEXIT_IMPL=OFF` (иначе shared libc++.so падает на
отсутствующем в musl символе). Проверено: на glibc-машине собран
x86_64-unknown-linux-musl host; бинарники запускаются на musl (Alpine),
компилируют+запускают C++, мульти-таргетны и кросс-компилируют под aarch64
(проверка через qemu).

Результат раскладывается в `hosts/<arch>-unknown-linux-musl/` (bin/, lib/,
include/, lib/clang/<ver>, share/licenses, host.mk).

== Отличия от glibc-хоста (musl-специфика)

* `LIBCXX_HAS_MUSL_LIBC=On` во всех сборках рантаймов — ключевой флаг;
* триплет `*-unknown-linux-musl`, загрузчик `ld-musl-<arch>.so.1`
  (явный `--dynamic-linker` не переопределяется — используется системный);
* libunwind обязателен (musl не несёт `libgcc_eh`);
* нет сборки GCC, GNU Make 4.3 и второй версии libc;
* `compiler-rt` вместо libgcc, `COMPILER_RT_DEFAULT_TARGET_ONLY=On` кладёт
  builtins в resource-dir.

== Опции

* *LTO* финального clang — настраивается `SP_LLVM_LTO`, *по умолчанию `Full`*
  (финальный тулчейн оптимизируется по максимуму). Облегчить: `SP_LLVM_LTO=Thin`;
  выключить: `SP_LLVM_LTO=` (например `make host SP_LLVM_LTO=`).
  При включённом LTO stage1 автоматически:
  - сериализует тяжёлые LTO-линковки (`LLVM_PARALLEL_LINK_JOBS=1`);
  - отключает LTO для нативной под-сборки tablegen
    (`CROSS_TOOLCHAIN_FLAGS_NATIVE`) — без этого lld падал при линковке нативных
    инструментов.
  *Full LTO проверен* на Alpine (musl 1.2.6): собирается и работает, пик памяти
  при `-O3 -DNDEBUG` умеренный (~18 ГБ). LTO применяется только к финальному
  clang (bootstrap stage0 — без LTO). На хостах с малой RAM можно ограничить
  параллелизм компиляции: `CMAKE_BUILD_PARALLEL_LEVEL=N make host`.

Kernel headers (пиннинг linux 5.10.258, `headers_install`) устанавливаются в
sysroot — их требует libc++ (`linux/futex.h`) и host-инструменты LLVM.
