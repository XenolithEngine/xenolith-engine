# Freestanding libc implementation

Some target systems do not have an acceptable libc implementation for running Xenolith Runtime. Specifically, these are Windows and WebAssembly.

Currently, only the Windows variant has been implemented.

## Windows

The implementation uses string and mathematical functions from musl libc. Some assembly implementations have been rewritten to conform to calling conventions.

Some wide character handling functions in musl libc are incompatible with Windows due to differences in wide character size. Such functions have been manually implemented.

A number of basic string functions are imported from ntdll.dll for better system compatibility.

File handling functions were inherited from musl libc but rewritten, since musl libc's synchronization primitives are not compatible with Windows.

unistd, fcntl, dlfcn, stat, and time functions have been manually implemented.

Application startup and shutdown functions have been manually implemented based on UCRT compliance.

MS C++ ABI functions for RTTI have been implemented.

mimalloc is used as the standard memory allocator.

Localization function support is limited. It is assumed that strings passed at the libc level are encoded in Unicode, so locale is not required for character classification. Comparison functions are fully implemented. Localized time output functions are not implemented. In general, it is not expected that applications will use libc functions for localization purposes; they are implemented for compilation compatibility.

POSIX signal functions are emulated at the application level.

mmap/munmap functions are fully implemented, however, they are significantly less efficient than on POSIX systems due to architectural differences.

dlfcn functions are fully implemented and use system DLL search rules.

dirent functions are fully implemented based on `FileIdBothDirectoryInfo`, thus avoiding the standard errors found in implementations based on FindFile.

### File descriptor inheritance and close-on-exec

A Windows kernel `HANDLE` is *not* inheritable by default. Unlike POSIX — where a freshly opened descriptor is inherited across `exec` unless `O_CLOEXEC` is requested — descriptors here are therefore **close-on-exec by default**. The mapping is the literal POSIX one:

* `FD_CLOEXEC` set means the underlying `HANDLE` is **non-inheritable** (`HANDLE_FLAG_INHERIT` clear).
* `FD_CLOEXEC` clear means the `HANDLE` is **inheritable** (it is passed to a child process created with `bInheritHandles = TRUE`).

Consequences:

* `open()` keeps the Windows default, so an opened descriptor is close-on-exec (`FD_CLOEXEC` set). To hand a descriptor to a child process the application must explicitly clear `FD_CLOEXEC` with `fcntl(fd, F_SETFD, 0)`, or open it with the non-standard `O_INHERITABLE` flag.
* `O_INHERITABLE` is a non-standard `open()` flag that requests an inheritable handle directly at open time — the opposite of `O_CLOEXEC`. Passing both `O_CLOEXEC` and `O_INHERITABLE` fails with `EINVAL`. It is surfaced on every platform for source portability, but is defined as `0` (no-op) everywhere except Windows.
* `fcntl` `F_GETFD` / `F_SETFD` report and set `FD_CLOEXEC` according to the rule above (set = non-inheritable, clear = inheritable).
* `dup()` and `dup2()` follow `open()`: the new descriptor is close-on-exec (non-inheritable).
* `dup3()` honours its `flags` explicitly — with `O_CLOEXEC` the new descriptor stays close-on-exec; without it, `FD_CLOEXEC` is removed and the new descriptor is inheritable.

This is an intentional divergence from POSIX, where descriptors (and the results of `dup`/`dup2`) default to inheritable-across-exec.
