# Архитектура сборки Xenolith

Xenolith использует make (чаще всего GNU Make) как основной сборщик. В отличии от других систем сборки, make отличается крайней стабильностью, переносимостью и долгосрочной поддержкой.

Вся архитектура сборки создана поверх Makefile.

## Кросс-компиляция по умолчанию

С точки зрения Xenolith, любая сборка это кросс-компиляция (аналогично подходу clang). При кросс-компиляции важно понимать  ключевую терминологию:

* `build` - ваша текущая система, в узком смысле, её штатный сборочный конвейер. Для большинства версий Linux это gcc версии, соответствующей той, что использовалась для сборки ядра. Для Apple это Apple Clang версии текущего SDK, для Windows - MSVC. При сборке Xenolith, `build toolchain` используется только при сборке `host toolchain` и зависимостей, и не используется для сборки конечного приложения.
* `host` - сборочный конвейер системы, который будет собирать конечное приложение. Предоставляется через Xenolith Runtime. Это - набор инструментов (`host toolchain`), запускающийся на текущей системе (возможно, через дополнительные средства, если его архитектура не совпадает с `build``), и компилирующий конечный код для `target`.
* `target` - целевая система для сборки приложения. Предполагается, что именно на этой системе конечное приложение будет запускаться.

* `build/host/target triple` - идентификатор системы. В Xenolith он всегда представлен в формате `<arch>-<vendor>-<os>[-<env>][+<variant>]`, где `arch` - архитектура процессора, `vendor` - поставщик платформы, `os` - тип ядра операционной системы, `env` - среда исполнения. <variant> отвечает за вариант поставки для целевой системы, в случае его отсутствия это пакеты для исходной целевой системы, в случае варианта `+sprt` - поставка на основе Xenolith Runtime.

Примеры идентификаторов:
*aarch64-pc-windows-msvc* - ОС Windows для архитектуры aarch64 (ARM64) на основе среды исполнения MSVC (msvcrt или UCRT). Поскольку Windows поставляется только для PC, это указано в поле `vendor`.

*x84_64-apple-macosx* - ОС MacOS для архитектуры x84_64. Среда исполнения опущена, значит, предполагается та, что используется для JC по умолчанию. Apple поставляет системы только для своего аппаратного обеспечения, потому в поле vendor указано apple.

*aarch64-apple-ios-simulator* - ОС Apple iOS для архитектуры aarch64 на основе симулятора iOS. Apple поставляет системы только для своего аппаратного обеспечения, потому в поле vendor указано apple.

*riscv64-unknown-linux-musl* - ОС Linux с musl libc в качестве среды исполнения (для glibc указывается gnu) для 64-битного варианта архитектуры RISC-V. Linux не имеет жёсткой привязки к аппаратному обеспечению, потому указывается unknown в поле vendor.

*riscv64-unknown-linux-android* - ОС *Android* для 64-битного варианта архитектуры RISC-V. С точки зрения сборки C/C++ Android это ядро Linux со средой исполнения на базе bionic libc, общепринято указывать среду исполнения как android. Linux не имеет жёсткой привязки к аппаратному обеспечению, потому указывается unknown в поле vendor.

## Host toolchain

В первую очередь, вам нужно получить набор инструментов для host, способный запускаться на вашей системе (чаще всего, он будет совпадать с build). Для Xenolith, он состоит из:
* Компилятора (clang)
* Линковщика (lld)
* Отладчика (lldb)
* Компилятора SPIR-V (glslc)
* Линковщика SPIR-V (spirv-link)
* Некоторых дополнительных инструментов сборки
* Ресурсных заголовков компилятора (они нужны для работы с его встроенными функциями бри сборке)

Структура обычно такая:
* `<host-toolchain-dir>/bin` - инструменты
* `<host-toolchain-dir>/lib` - библиотеки, необходимые для запуска инструментов
* `<host-toolchain-dir>/lib/clang/<ver>/include` - ресурсные заголовки компилятора
* `<host-toolchain-dir>/lib/clang/<ver>/lib` - ресурсные библиотеки компилятора (опционально)
* `<host-toolchain-dir>/share` - дополнительные файлы, включая лицензии на используемое открытое ПО.

Ресурсные библиотеки обычно включаются в целевой набор, но на платформах, где их сборка при кросс-компиляции невозможна, они также будут и здесь. Это необходимо для сборки целевого набора и не используется при сборке самих приложений.

Набор инструментов содержит файл host.mk, в котором описано, где искать нужные инструменты, а также дополнительные флаги компиляции, которые нужны для всякой сборки с использованием этого набора.

Система сборки ищет файл host.mk так:
1. Проверяет <xenolith-engine-repo>/toolchains/hosts/<host-triple>/host.mk (здесь хранятся загруженные вручную данные)
2. Проверяет <xenolith-engine-repo>/runtime/toolchains/hosts/<host-triple>/host.mk (здесь хранятся собранные на текущей машине инструменты)
3. Завершается с ошибкой, если не найдено

## Target

Далее, для сборки нужны базовые библиотеки системы (или их вариант в версии Xenolith Runtime) и библиотеки зависимостей. Они формируют целевой набор.

Структура набора:

* `<target-dir>/include` - системные заголовки цели (когда они необходимы, чаще всего их нет)
* `<target-dir>/include_libc` - заголовки стандартной libc цели, там, где их распространение разрешено лицензией
* `<target-dir>/lib` - базовые библиотеки платформы. Чаще всего это не полные библиотеки, а урезанные скрипты для сборки приложения, которые позволят приложению использовать библиотеки на самой платформе, но не содержат в себе кода.
* `<target-dir>/lib/clang/lib/<os>` - ресурсные библиотеки компилятора для целевой платформы
* `<target-dir>/usr/include` - заголовки пользовательского окружения, включая зависимости
* `<target-dir>/usr/lib` - библиотеки зависимостей
* `<target-dir>/share` - дополнительные файлы, включая лицензии на используемое открытое ПО

Набор структурирован так, чтобы использовать его в качестве sysroot компилятора.

Файл target.mk описывает, как собирать код для данной целевой платформы. Система сборки ищет файл target.mk так:
1. Проверяет <xenolith-engine-repo>/toolchains/targets/<target-triple>/target.mk (здесь хранятся загруженные вручную данные)
2. Проверяет <xenolith-engine-repo>/runtime/toolchains/targets/<target-triple>/target.mk (здесь хранятся собранные на текущей машине зависимости)
3. Завершается с ошибкой, если не найдено

Для сборки под целевую платформу, укажите `STAPPLER_TARGET=<target-triple>` при запуске начального файла make.

## Как добавить свой инструмент сборки или библиотеку зависимости

В большинстве случаев, вы можете использовать сторонние библиотеки и средства сборки без интеграции их в систему сборки Xenolith, просто используя систему сборки более высокого уровня или описывая их в качестве подключаемых библиотек на уровне приложения.

Добавлять инструмент или библиотеку непосредственно в систему сборки Xenolith может потребоваться, если вы хотите автоматизировать сборку или получить полностью воспроизводимый результат.

Если вам действительно необходимо встроить в систему свой инструмент, нужно использовать тот же подход, что использует Xenolith Runtime при сборке инструментов. В первую очередь, необходимо собрать из исходных кодов набор инструментов или целевой набор (см. `runtime/toolchains/README.adoc`).

В качестве промежуточного результата сборки, Xenolith Runtime сохраняет полную версию sysroot для сборки, включая файлы cmake и pkgconfig для автоматического поиска зависимостей. Используя этот sysroot, вы можете собрать свои инструменты для использования в host или target для Xenolith Engine.

Для добавления зависимости в целевой набор, используйте sysroot `runtime/toolchains/target-<os>/intermediate/<target-triple>`.

Для добавления инструмента в набор сборки, используйте `runtime/toolchains/host-<os>/sysroot-out`.

## Воспроизводимая сборка

Полностью воспроизводимая сборка - одна из задач Xenolith Runtime. По этой причине используется строго фиксированные версии инструментов и зависимостей.

Для обеспечения воспроизводимой сборки, всё, что вам необходимо - предоставить базовое воспроизводимое окружение (chroot), в который можно установить и из которого можно собрать все инструменты для Xenolith Runtime.

После того, как вы соберёте host toolchain в воспроизводимом окружении, дальнейшая сборка Xenolith и конечного приложения будет полностью воспроизводимой.
