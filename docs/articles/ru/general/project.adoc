# О проекте Xenolith

Проект Xenolith состоит изз нескольких частей:

* **Xenolith Runtime** (ранее Stappler Runtime) - библиотека, предоставляющая базовый интерфейс для языков C и C++ (то есть, реализация libc и C++ STL).
* Stappler utilities - набор дополнительных инструментов, таких, как работа с HTML, JSON, интерфейс к БД, интерфейс сетевых запросов.
* **Xenolith Engine** - графический и вычислительный движок на базе Vulkan, основная часть проекта.
* Сборочная система и инструменты сборки Xenolith - собственная универсальная система сборки для приложений на базе Xenolith Runtime.

Все это в совокупности формирует **Xenolith SDK** - пакет для разработки кроссплатформенных приложений.

## Принципы Xenolith

Каждый проект имеет принципы, на основе которых принимаются те или иные архитектурные и технические решения. Для Xenolith они такие:

### 1. Xenolith SDK не ставит перед пользователем барьеров, юридических или технических

Такие барьеры, создают, например:
* MacOSX SDK, когда требует использования только на аппаратной части от Apple
* Windows SDK, когда запрещает распространять в составе других продуктов свои заголовки и импортируемые библиотеки.
* Различные библиотеки под лицензией GNU GPL, когда требуют публиковать производный продукт под открытой лицензией и создают ограничения для публикации в магазинах приложений.

Если Xenolith SDK не может снять эти ограничения сейчас, то будет стремиться обойти их в будущем.

### 2. Xenolith SDK создаётся для C и C++

Мы решаем задачи, которые для других языков, таких. как java, Rust, Go, Python могут быть уже решены. Однако, мы делаем это для C и C++. Именно для этих языков мы обязуемся предоставлять удобное и функциональное рабочее окружение.

Это не значит, что нас не волнует поддержка других языков, но мы занимаемся этим не более, чем требует взаимодействие на уровне динамических библиотек.

Решение о переписывании инструментов на другой язык никогда не будет принято.

### 3. Единообразие в API

Все поддерживаемые платформы должны получать единый интерфейс, насколько это технически возможно.

Ключевая проблема, из которой появился Xenolith SDK - несовместимость различных версий C и C++, предоставляемых платформами. В частности:

* Различные наборы функций в glibc, bionic libc, libSystem на MacOS и UCRT на Windows. Более того, эти наборы функций меняются от версии к версии и в зависимости от передаваемых флагов.
* Различные версии libc++ в MacOS SDK и Android NDK;
* Значительные различия в реализации C++ на Windows по сравнению с другими платформами.

Пользователь Xenolith SDK должен быть уверен, что его код будет собираться и работать на любой поддерживаемой платформе без массивного configure скрипта или огромного описания для CMake.

Чем меньше зависимое от платформы подмножество кода - тем мы ближе к цели.

### 4. Единообразие в сборке

Сборка конечного приложения должна выполняться единообразно.

Пользователь Xenolith SDK не должен задумываться о том, какие флаги и возможности есть у конкретного компилятора под конкретную платформу.

Пользователь не должен задумываться, какой на его платформе отладчик и как с ним взаимодействовать.

Пользователь не должен задумываться, какие дополнительные средства сборки, пакеты и библиотеки ему нужны, чтобы начать работу.

Пользователь должен просто собирать код, и этот код должен работать.

### 5. Совместимость с внешними библиотеками

Любой код, собранный в динамически подключаемую библиотеку, должен работать с Xenolith SDK на поддерживаемых платформах.

Xenolith SDK не должен создавать проблем для работы такого кода.

### 6. Xenolith SDK - технический проект

Он не является политическим, экономическим, юридическим, этическим, мировоззренческим или ещё каким-то заявлением.

Люди, причастные к проекту, могут высказывать подобные заявления до тех пор, пока эти заявления не становятся основанием для принятия технических решений.

### 7. Участник проекта несёт полную ответственность за свои действия

Не важно, использовались ли интеллектуальные инструменты в действиях участника, ответственность за результат этих действий он несёт исключительно. Интеллектуальные помощники любого рода, будь то нейросети или другие средства - не более, чем инструменты. Мы не признаём их соавторство и их ответственность.

Если инструмент сгенерировал код, и этот код был отправлен в проект - авторство этого кода целиком признаётся за человеком, и на этом основании принимаются дальнейшие решения.

Мы допускаем использование любых инструментов, но за низкий уровень качества результата их применения несёт ответственность человек.

В оценке качества мы опираемся, кроме очевидных моментов работоспособности, на проверяемость, поддерживаемость, логику интеграции в проект. 

### 8. Заключительные основания

Если какой-то из принципов не может быть выполнен прямо сейчас - необходимо стремиться к этому выполнению, создавать условия для выполнения этого принципа. В том числе, через взаимодействие с другими проектами, так или иначе связанных с выполнением принципов Xenolith.

## Архитектурные и технические решения, основанные на принципах Xenolith

### 1. Xenolith SDK не ставит перед пользователем барьеров, юридических или технических

* Отказ от UCRT и использования заголовков SDK на Windows
* Реализация сборки для Android без использования NDK
* Реализация сборки на MacOS без использования MacOS SDK

### 3. Единообразие в API

* Реализация Xenolith Runtime как зонтичной libc на всех платформах
* Собственная (частичная) реализация C++ STL
* Собственная реализация pthread

### 4. Единообразие в сборке

* Использование собранных в контролируемом окружении инструментов LLVM
* Поставка всех инструментов сборки в составе SDK
* Использование фиксированной версии GNU Make в качестве основного сборщика

### 5. Совместимость с внешними библиотеками

* Отказ от использования libc++ в качестве C++ STL
* Использование изолированных статических версий C++ ABI на Linux, Android, Windows
* Использование системной библиотеки libc++abi на MacOS
