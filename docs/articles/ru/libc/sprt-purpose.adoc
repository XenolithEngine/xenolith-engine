# Цель существования Xenolith Runtime

Первоначальная задача Xenolith Runtime - поддержка компиляции и запуска кода на языках C и C++, сгенерированного внешними инструментами независимо от пользовательской системы.

То есть, ключевые задачи:
1. Обеспечить стабильное по API и ABI окружение времени исполнения для кода на C и C++.
2. Обеспечить компиляцию кода на C и C++ с одной платформы на любые другие поддерживаемые пользовательские платформы
3. Не требовать от пользователя дополнительных усилий при установке, как то: установка SDK платформы, установка пакетов зависимостей, установка специальных инструментов для компиляции.
4. Работать с библиотеками пользовательской системы, не накладывая на них и на пользовательский код дополнительных требований.
5. Не требовать дополнительных зависимостей для запуска готового кода, кроме самого окружения времени исполнения.

В итоге, предполагается получить пакет, который может быть внедрён в целевое приложение, которое сможет использовать его для компиляции кода на C/C++ как на текущую платформу, так и на любую другую поддерживаемую, и запуска этого кода.

## Базовые компоненты времени окружения

Базовые компоненты, такие, как:
- работа со строками
- реализация base16/base64/base64url
- подсистема пулов памяти
- функции времени
- поддержка Unicode
- классификатор местоположения в файловой системе
- функции геометрии
- высокоуровневый диспетчер событий
- интерфейс к оконной системе
- инструмент автоматического подсчёта ссылок
- разбор URL
 унаследованы от исходного проекта libstappler.
 
 От него же получено название базового пространства имён sprt - "Stappler Portable Runtime". Позже проект переименован в Xenolith Runtime.

## Зонтичная библиотека libc

Проект должен предоставлять единый базовы интерфейс для сборки и поддержки кода на языке C. Эта задача решена при помощи создания "зонтичной" libc, которая создаёт слой абстракции между реальной libc платформы и интерфейсом, который будет доступен приложениям.

За базовый интерфейс и основу для поведения функций выбрана musl libc, как наиболее зрелая открытая реализация, не накладывающая лицензионных ограничений на проект.

Этот интерфейс максимально унифицирован в разрезе имён функций и базовых структур, однако, использует  набор констант, извлечённый из исходной libc. Также, приняты решения об унификации типов time_t и off_t, во всех случаях используются 64-битные значения.

В ряде случаев, интерфейс зонтичной libc реализует функции, отсутствующие в исходной libc, или изменяет поведение функций таким образом, чтобы она работала одинаково на всех платформах. За опорное поведение принято поведение musl libc на Linux.

Заголовки зонтичной libc имеют 3 слоя.

1. Базовый слой (файлы с префиксом `__sprt`). Это - самая основа реализации libc, содержат базовые функции и константы. Всё содержимое этих файлов должно содержать префикс `__sprt` или `__SPRT`, чтобы изолировать их содержимое от платформенной libc. Эти файлы могут быть включены одновременно с платформенной libc.
2. Обёрточный слой (расположен в "/include/sprt/wrappers"). Это - слой совместимости, обеспечивающий работу С и С++ в различных условиях включения файлов. не предполагается, что эти файлы могут быть включены вместе с платформенной libc.
3. Зонтичный слой (расположен в "/include_libc"). Это заголовки стандартной POSIX libc, которые перенаправляют стандартные функции в обёрточный и базовый слои. Функции в нём реализованы как обёртки вокруг функций базового слоя, которые не должны иметь собственного представления в ABI.

В условиях, когда платформенной libc не существует (для Windows и Wasm), зонтичный слой может играть роль базовых заголовков libc, не порождая обёрток.

Некоторые функции не могут быть реализованы на целевой платформе. В таком случае, для них существуют флаги `__SPRT_CONFIG_*`, с помощью которых можно определить, есть ли они для текущей платформы. Однако, концепция Xenolith Runtime предполагает, что эти функции доступны всегда, но в случае недоступности на платформе - будут возвращать код ошибки, показывающий их отсутствие (обычно - `ENOSYS`).

### pthread

Xenolith Runtime реализует свой интерфейс pthread на всех платформах, включая и функции работы с потоками. и примитивы синхронизации. Эта реализация существенно ограничена в использовании различных системных часов, однако, гарантирует единообразие поведения потоков, примитивов и реализованных функций.

### setjmp/longjmp

Для единообразной работы завершения потока требуется единообразная работа longjmp для корректного разворачивания стека и вызова деструкторов. Xenolith Runtime реализует корректный вызов деструкторов во время longjmp для всех платформ.

### Интерфейсы платформы

Платформно-зависимые интерфейсы, такие, как epoll, kqueue, timerfd и другие есть в API зонтичной libc всегда. Функции доступны на всех платформах (как предполагает цель Xenolith Runtime), но если интерфейс не доступен на самой платформе - функции возвращают соответствующий код ошибки (`ENOSYS`)

## Поддержка C++

Изначально, предполагался выбор llvm libc++ в качестве основного интерфейса C++. Однако, от этого пришлось отказаться, поскольку мы не можем единообразно предоставить LLVM libc++ для всех платформ. В первую очередь, препятствия создают платформы BSD и MacOS, где libc++ используется в качестве системной. В этом случае поставка отдельной libc++ создаёт неоднозначность для линковщика при использовании другими библиотеками системных библиотек, что противоречит 4 задаче Xenolith Runtime.

По этой причине, Xenolith Runtime реализует базовый API С++ внутри себя, используя пространство имён `sprt` как `std`. Эта реализация в своей основе взята из LLVM libc++. Ключевые отличия в реализации примитивов синхронизации и контейнеров, которые основаны на унаследованном от libstappler коде.

Все контейнеры С++ Xenolith Runtime (а также реализация `function``) могут использовать аллокацию памяти на основе пулов памяти и стандартную на основе malloc. Кроме того, эти контейнеры адаптированы к использованию в Xenolith Engine и могут не следовать определённому стандартом поведению.

С++ Xenolith Runtime не предполагает реализацию исключений, поскольку это невозможно выполнить единообразно с позиции ABI. Потому, некоторые ситуации, где исключения служат единственным способом обработки ошибок в стандарте C++, реализованы нестандартным способом.

Также, запрещены стандартные операторы new и delete, их использование может вызвать неоднозначность в ABI. В порождаемых предупреждениях описаны альтернативные подходы. Исключение - автоматически порождаемые операторы в деструкторах. Поскольку исключения не используются, такие операторы никогда не будут вызваны.

В других случаях, С++ Xenolith Runtime должен следовать стандарту C++20 в реализованных функциях.

## Набор инструментов

Xenolith Runtime использует clang в качестве компилятора, инструменты из набора llvm для других целей сборки, GNU Make в качестве основного сборщика. В редких случаях (например, для подписи поставляемых на MacOS приложений) могут потребоваться сторонние инструменты.

Принципы Xenolith Runtime требуют, чтобы на любой платформе компилятор работал единообразно, потому для работы необходимо взять готовый бинарный пакет с набором инструментов, либо собрать его из исходного кода, работа со штатными версиями LLVM в составе ОС не гарантируется. Сборочные скрипты для всего поставляются в директории "/toolchains".

### Принцип обновления LLVM

Мы обновляемся на последнюю выпущенную версию LLVM в серии, как только начинается релиз новой серии. То есть, мы обновляемся на 21.1.8, когда выпущена 22.1, и обновимся на 21.1.X, когда будет выпущена 23.1.

Так мы используем наиболее стабильную версию, с наибольшим числом исправлений после добавления новых функций.


## Вопросы лицензирования

Xenolith Runtime лицензируется под MIT License в исходном коде. При бинарной поставке в составе набора инструментов ситуация более сложная.

### Общее

В состав набора инструментов всегда входит GNU Make. Поскольку он используется только как внешнее приложение, лицензионных ограничений не накладывается.

### Linux

Для Linux, в состав набора инструментов входит версия libc, предназначенная для линковки конечного приложения, её заголовки, и заголовки минимально необходимой версии операционной системы. При этом, заголовки используются только на этапе сборки Xenolith Runtime и не влияют на сборку конечного приложения. Также, libc используется только для поиска функций во время линковки, и далее не используется.

Это значит, что приложения, собранные с помощью Xenolith Runtime, не являются "combined work" в терминах GNU GPL и не попадают под правила этой лицензии, если используется glibc.

### Android

Для Linux, в состав набора инструментов входят версии bionic libc и компоненты ОС, предназначенные для линковки. Библиотеки и заголовки взяты из версии NDK с длительным сроком поддержки. Библиотеки обработаны с помощью llvm-ifs для уменьшения размера.

Заголовки и библиотеки из состава NDK поставляются под Apache License.

### MacOS/iOS

Пакеты SDK для этих систем не включаются в бинарную поставку из-за ограничений лицензии, однако, они устанавливаются автоматически при переключении MacOS в режим разработчика.

### Windows

Для Windows, оригинальные файлы из SDK не используются и не требуются для работы. Дополнительные ограничения не накладываются.
