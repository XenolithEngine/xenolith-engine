= Портирование Xenolith: введение и общие термины
:toc:
:toclevels: 2

Этот раздел описывает, как перенести движок на новое железо или новую операционную систему. Он
состоит из трёх планов и этого вводного файла:

[cols="1,3", options="header"]
|===
| Документ | Когда он нужен

| xref:new-arch.adoc[План А. Новая архитектура процессора]
| Движок уже работает на нужной ОС (например, Linux), но не на нужном процессоре (например, LoongArch
  или будущий RISC-V с другим ABI).

| xref:new-target-os.adoc[План Б. Новая ОС как target]
| Нужно, чтобы *приложения* на Xenolith запускались на новой ОС (NuttX, Embox, FreeBSD, своя
  микроядерная система). Собирать приложения при этом можно на привычной машине с Linux.

| xref:new-host-os.adoc[План В. Новая ОС как host]
| Нужно, чтобы *сам набор инструментов* (clang, lld, make, xenolith-cli) работал на новой ОС и
  собирал на ней приложения.
|===

Планы опираются друг на друга. Термины, которые встречаются во всех трёх, определены здесь один
раз. Если в тексте плана встретилось незнакомое слово — сначала ищите его в
<<glossary,словаре>> ниже.

Документы написаны для человека, который знает C/C{pp} и make, но не знает устройства движка. Каждый
шаг объясняет, *зачем* он нужен, *что* именно поменять и *как убедиться*, что шаг сделан.

Английская версия раздела — link:../../en/porting/index.adoc[`docs/articles/en/porting/`].

== Как планы связаны между собой

----
                 ┌──────────────────────────┐
                 │ План А: архитектура      │  новая строка в списках архитектур
                 │ (для уже известной ОС)   │  и шесть заголовков ABI
                 └────────────┬─────────────┘
                              │ архитектура уже есть
                              ▼
                 ┌──────────────────────────┐
                 │ План Б: ОС как target    │  платформенный слой runtime,
                 │                          │  sysroot, пресет make
                 └────────────┬─────────────┘
                              │ ОС уже target
                              ▼
                 ┌──────────────────────────┐
                 │ План В: ОС как host      │  набор инструментов, собранный
                 │                          │  *для* этой ОС и *на* ней работающий
                 └──────────────────────────┘
----

Отсюда три правила порядка работы:

. *Новая ОС сначала становится target, и только потом — host.* Host-набор — это обычная программа
  (clang, lld, xlmake), собранная движком *под* новую ОС. Пока движок не умеет собирать программы под
  эту ОС, собрать для неё host нельзя. Это не теоретическое правило: в истории репозитория цель
  macOS появилась на день раньше host-набора macOS, а host Windows собирается против цели
  `<arch>-pc-windows-msvc+dll`.
. *Новую ОС переносят сначала на уже поддержанной архитектуре.* Если ОС работает и на aarch64, и на
  чём-то экзотическом — начинайте с aarch64 или x86_64: тогда половина заголовков ABI уже есть, и
  ошибки будут только «про ОС». Вторая архитектура добавляется потом по плану А (так был устроен
  перенос на микроядро Tau: сначала aarch64, отдельным этапом — x86_64).
. *Новая архитектура сначала добавляется для Linux.* Linux — эталонная платформа движка: на нём
  собираются все наборы инструментов, на нём есть qemu-user для запуска чужих бинарников. Android,
  Windows и macOS для новой архитектуры — отдельные необязательные шаги плана А.

== Словарь

=== Машины и наборы инструментов

Движок считает любую сборку кросс-компиляцией. Полное описание — в
link:../general/build.adoc[Архитектура сборки Xenolith]; здесь — коротко.

build-машина::
  Компьютер, на котором вы *собираете набор инструментов* из исходников. Используется только на этапе
  изготовления host-набора (её системный gcc или clang собирает первый, «затравочный» clang). Для
  сборки приложений не используется. Все выпускаемые наборы сейчас собираются на x86_64 Linux.

host::
  Система, на которой *работают инструменты* Xenolith и где разработчик собирает приложение.
  Сейчас это Linux (glibc и musl), Windows и macOS.

target (цель)::
  Система, на которой *работает собранное приложение*. Целей больше, чем host-систем: к перечисленным
  добавляются Android, iOS, WebAssembly, NuttX, Embox.

triple (тройка)::
  Строка-идентификатор системы: `<arch>-<vendor>-<os>[-<env>][+<variant>]`. Примеры:
  `x86_64-unknown-linux-gnu`, `aarch64-pc-windows-msvc`, `riscv64-unknown-linux-musl`,
  `aarch64-nuttx-none-elf`. Часть `+<variant>` — вариант поставки: `+open` (sysroot macOS без Xcode),
  `+dll` (Windows вокруг `sprt.dll`), `+user` (Embox в пользовательском режиме). Тройку цели передают
  в сборку как `STAPPLER_TARGET=<triple>`.

host-набор (host toolchain)::
  Каталог `hosts/<host-triple>/` с компилятором clang, линковщиком lld, отладчиком lldb, компилятором
  шейдеров glslang, `spirv-link`, утилитами llvm и `make`/`xlmake`. Описывается файлом `host.mk`.
  Подробно — в xref:new-host-os.adoc#host-contract[плане В].

целевой набор (target sysroot)::
  Каталог `targets/<target-triple>/`: заголовки и библиотеки цели, LLVM-библиотеки времени исполнения
  (compiler-rt, libc{pp}abi, libunwind) и собранные под цель зависимости (zlib, freetype, curl, …).
  Описывается файлом `target.mk`. Подробно — в xref:new-target-os.adoc#target-mk[плане Б].

`host.mk`, `target.mk`::
  Маленькие make-файлы, которые лежат в корне набора и говорят системе сборки, где искать
  инструменты (`HOST_CC`, `HOST_CXX`, …) и с какими флагами собирать под цель (`TARGET_NAME`,
  `TARGET_SYSTEM`, `TARGET_ARCH`, `TARGET_GENERAL_CFLAGS`, …). Ищутся сначала в `toolchains/`
  (скачанные наборы), потом в `runtime/toolchains/` (собранные на этой машине) — см.
  `make/utils/defaults.mk`.

нативный host и cross host::
  Нативный host собирается на build-машине *для неё самой* многоступенчатой раскруткой
  (bootstrap): `make -C runtime/toolchains host`. Cross host (`make host-cross-<triple>`) собирается
  уже готовым нативным clang *для другой системы* — против целевого набора этой системы. Все
  host-наборы, кроме x86_64 Linux, сейчас — cross host.

=== Слои движка

Xenolith Runtime, sprt::
  Нижний слой движка (каталог `runtime/`, пространство имён `sprt`). Единая для всех платформ
  «зонтичная» libc, свой C{pp} (`sprt` вместо `std`), потоки, часы, файловая система, цикл событий,
  окна. Зачем он нужен — в link:../libc/sprt-purpose.adoc[Цель существования Xenolith Runtime].
  Почти вся работа по портированию происходит именно здесь.

платформенный макрос::
  `SPRT_LINUX`, `SPRT_WINDOWS`, `SPRT_NUTTX`, `SPRT_WASM`, … Определяется *только* в
  `runtime/include/sprt/c/bits/__sprt_def.h` по предопределённым макросам компилятора. Весь код
  движка проверяет платформу через `#if SPRT_X` (не `#ifdef`!). Правила — в
  link:../../../usage/codestyle/platform/platform-guards.adoc[platform-guards.adoc].

идентификатор архитектуры::
  `__SPRT_ARCH_ID` и `__SPRT_ARCH_NAME`, определяются там же. ID — число (AARCH64=1, X86_64=4,
  RISCV64=8, LOONGARCH64=10, …), имя — каталог с заголовками ABI (`aarch64_sprt`).

cross-заголовки::
  Каталог `runtime/include/sprt/c/cross/<os>_sprt/` и его подкаталоги `<arch>_sprt/`. В них — числа,
  которые у каждой ОС и архитектуры свои: коды `errno`, флаги `O_*`, номера сигналов и системных
  вызовов, размер `jmp_buf`, раскладка `fenv_t`. Остальные заголовки sprt берут числа отсюда.

config gate, `__SPRT_CONFIG_HAVE_*`::
  Флаг «есть ли на платформе такая функция» (`epoll`, `fork`, `timerfd`, …). Если платформа функцию
  не даёт, флаг ставится в 0 в `config.h` платформы; функция при этом всё равно существует, но
  предупреждает при компиляции и возвращает `ENOSYS`. Так код остаётся переносимым без `#if`.

hosted и freestanding цель::
  *Hosted* — у ОС есть своя libc, и sprt *оборачивает* её (`runtime/libc_wrapper`): Linux, Android,
  macOS, NuttX, Embox. *Freestanding* — своей libc у ОС нет или она непригодна, и sprt *сам является*
  libc (`runtime/libc_impl` + части musl + mimalloc): Windows, WebAssembly, Embox в режиме EL0.
  Выбор между ними — главное решение xref:new-target-os.adoc#forms[плана Б].

`TARGET_SYSTEM` и OS-пресет::
  `TARGET_SYSTEM` — имя системы из `target.mk` (`Linux`, `Windows`, `NuttX`, `EmboxUser`, …). По нему
  `make/utils/apply-toolchain.mk` подключает пресет `make/os/<os>.mk`: суффиксы файлов, флаги
  компиляции, способ компоновки.

цикл событий, Looper, dispatch::
  Реактор, через который движок ждёт ввод-вывод, таймеры и процессы (`runtime/src/dispatch/`).
  У каждой ОС свой бэкенд: io_uring и epoll на Linux, kqueue на macOS, IOCP на Windows, свой — на NuttX
  и wasm.

контроллер окон::
  `ContextController` в `runtime/window/<os>/`: создаёт окна и поверхности для отрисовки на конкретной
  оконной системе. Режим без окна (`--headless`) есть на любой цели.

графический бэкенд::
  `xenolith/backend/vk` (Vulkan), `xenolith/backend/webgpu` (браузер), `xenolith/backend/soft`
  (программный растеризатор — работает везде, где есть процессор).

=== Исходники и сборка

SCU и подъюнит::
  Модуль компилируется одним файлом `*.cpp` (SCU — single compilation unit), который подключает
  `*.cc`-файлы через `#include`. Изменение только `.cc` make *не замечает*: после правки
  `touch`-ните заголовок или `.cpp`, который его включает, и убедитесь, что строка компоновки
  действительно появилась в выводе.

`xlmake`::
  Совместимый с GNU make сборщик, написанный на самом движке (`utils/xlmake`). Ему не нужна оболочка
  `sh`: команды вроде `$(MKDIR)` и `$(CP)` он выполняет сам. На Windows это единственный make.

`xenolith-cli`::
  Установщик и сборщик (`utils/installer`): скачивает наборы с сервера в своё хранилище, связывает их с
  каталогом движка и запускает сборку. Предпочтительный способ собирать проекты; голый `make` —
  запасной.

релиз SDK::
  Каталог `sdk-v*` на сервере релизов с архивами `hosts/<triple>.tar.xz` и `targets/<triple>.tar.xz` и
  подписями `.sig`. Списки того, что входит в релиз, — `RELEASE_HOSTS` и `RELEASE_TARGETS` в
  `runtime/toolchains/Makefile`.

qemu-user и qemu-system::
  qemu-user запускает отдельный бинарник чужой архитектуры на вашем Linux (`qemu-riscv64 ./prog`) — им
  проверяют план А. qemu-system эмулирует целую машину с ОС — им проверяют план Б для встраиваемых
  ОС.

== Вспомогательные скрипты

В `utils/porting/` лежат скрипты на Python, которые проверяют этапы портирования. Они только читают
дерево движка, наборы инструментов и sysroot, ничего не правят и не собирают. Каждый печатает отчёт
по шагам плана: `OK` — сделано, `FAIL` — обязательная часть отсутствует или неверна, `WARN` — вероятная
проблема или отсутствует необязательная часть.

[cols="1,2,1", options="header"]
|===
| Скрипт | Что проверяет | Шаги

| `check-arch.py <arch>` | всё, что план А требует от архитектуры | А1–А12
| `check-target-os.py <os>` | всё, что план Б требует от целевой ОС | Б2–Б12
| `check-host-os.py` | всё, что план В требует от host-ОС | В1–В11
| `detect-host.py` | что думает о текущей машине каждый детектор host и совпадают ли ответы | В1–В3
| `check-sysroot.py` | целевой набор по контракту `target.mk` | А5, Б4
| `check-toolchain.py` | host-набор по контракту `hosts/<triple>`; с `--run` — ещё и запуск инструментов | А9, В4, В6
| `check-abi.py` | числа cross-заголовков sprt против настоящей libc цели, включая номера системных вызовов | А3, Б3, Б7
| `find-refs.py` | строки, где упомянут эталон (`riscv64`, `SPRT_NUTTX`), но нет нового имени: списки, в которые порт ещё не добавлен | все
|===

Подробности и примеры — в link:../../../../utils/porting/README.adoc[utils/porting/README.adoc].

== Условные обозначения

* Пути без префикса отсчитываются от корня репозитория движка (`xenolith-engine/`).
* `<arch>` — имя архитектуры в тройке (`loongarch64`), `<os>` — имя ОС в нижнем регистре (`nuttx`),
  `<OS>` — то же для макросов (`NUTTX`), `<System>` — значение `TARGET_SYSTEM` (`NuttX`),
  `<triple>` — полная тройка.
* Шаги планов пронумерованы: *А1…А12*, *Б1…Б13*, *В1…В11*. Ссылки «см. Б6» ведут в соответствующий
  план.
* Каждый шаг заканчивается блоком *«Готово, когда»*. Это определение завершённости. Если проверка не
  проходит, шаг не сделан, даже если код написан.
* Номера строк в документах не указываются — они устаревают. Ищите по имени файла и символа.

== Правила, общие для всех трёх планов

*Собирайте через систему сборки, а не руками.* Никогда не вызывайте `clang` или `cmake` напрямую,
«чтобы проверить». Флаги, sysroot и порядок модулей задаёт make. Используйте
`xenolith-cli build <проект> --target <triple>` или `make -C <проект> STAPPLER_TARGET=<triple>`.

*Код под чужим `#if` не компилируется на вашей машине.* Сборка под Linux пропускает всё, что под
`#if SPRT_WINDOWS` или `#if SPRT_NUTTX`. Значит, правку платформенного кода можно проверить только
сборкой под эту платформу. Таблица «что менял → чем проверять» —
link:../../../agents/cross-target.md[cross-target.md].

*Самая маленькая проверка — `tests/runtime`.* Проект `tests/runtime` (бинарник `runtimetest`)
использует только модули runtime и при компиляции проверяет около тысячи `static_assert`-ов,
сверяющих числа sprt с числами настоящей libc. Его сборка под новую цель — первая и самая полезная
проверка в планах А и Б. Отдельные разделы запускаются по имени: `runtimetest libc_uname libc_setjmp`.

*Общие заголовки касаются всех платформ.* `__sprt_def.h`, `cross/__sprt_config.h`, `include_libc/`
читаются при каждой сборке под каждую цель. Правка в них проверяется не только на новой платформе, но
и прогоном `tests/run-checks.py full` на host-машине плюс сборкой `tests/runtime` под Windows, Android
и wasm. Протокол — link:../../../agents/test-protocol.md[test-protocol.md].

*Один слой — один коммит.* Порты, которые легко читать в истории (loongarch64, Tau), разбиты так:
платформенные макросы → заголовки ABI → сборка → платформенный слой → окно → инструменты →
документация. Огромный единый коммит («добавлена поддержка X», 127 файлов) потом невозможно
разобрать.

*Документацию обновляют в том же заходе.* Каждый план заканчивается списком документов, где
перечислены поддерживаемые платформы. Их обновляют вместе с портом, иначе следующий человек
наткнётся на устаревшие таблицы.
