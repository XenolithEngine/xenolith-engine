# libc для windows. История о чувстве острого дефицита свободы.

## Вступление

Если я хочу поставлять приложение на С/С++ на Windows, у меня есть два широко известных варианта. Первый - использовать Microsoft Visual C/C++, и поставлять приложение либо в статической форме, либо с redistributable пакетом. Либо, можно пойти по пути MinGW, и нести с собой уже их DLL.

Если же я не хочу нести с собой DLL, остаётся либо вариант с MSVC, либо публиковаться под GPL, иначе с MinGW будет конфликт лицензий.

Если же я хочу поставлять приложение без DLL, которое будет собирать другие приложения... либо GPL, либо... никак.

Потому, что для сборки нового приложения нужны import libs, а распространять эти import libs из состава Windows SDK запрещено лицензией Microsoft. Остаётся два варианта: заставлять пользователей устанавливать MSVC, или уходить с этого чёртова устаревшего C++ на язык, где за меня уже кто-то решил эту проблему.

А если я не хочу уходить с любимого языка?

Если я хочу, чтобы мне не заламывали руки что со стороны Microsoft, что со стороны GPL?

Программист я или нет? Я напишу код и решу проблему.

Конечно же, история целиком намного сложнее. Первая и главная проблема, почему я вообще дошёл до создания libc - кроссплатформенная совместимость. Интерфейс UCRT, вроде как, напоминает POSIX libc местами, но в реальности, часто проще делать слой POSIX libc, и слой Windows API, игнорируя безобразную UCRT. Так и путаницы меньше, и небольшой выигрыш в производительности будет, за счёт удаления одного слоя.

А ещё кросскомпиляция и танцы с бубном вокруг LLVM, чтобы на одном CI собрать и Windows, и Linux.

Ах, если бы была библиотека с реально единообразным интерфейсом...

Значит, будет.

## С чего начать

Многих технарей возмущает это, но порядок вещей таков - начинать нужно с юридических моментов. А именно - дозволено ли законом делать то, что я собираюсь сделать.

Вопрос не праздный. А что я вообще собираюсь сделать?

Я собираюсь сделать некую систему, которая без Windows SDK и MinGW в наличии будет собирать мне графические приложения для Windows. А именно, собирать графические приложения, которые сами смогут собирать графические приложения. Не изобретая для этого очередной новый язык, коих развелось десятки тысяч - по парочке на коммерческую контору в ИТ. Я хочу C++, и даже шайтан меня в этом не разубедит.

Для этого, мне нужно исполняемое ядро libc (оно же startup code), и заголовки для работы с Windows API без копирования их из SDK (запрещено лицензией).

Начнём с заголовков. Придётся вспомнить 2021 год и тяжбу Oracle vs. Google на тему публичного API Java. Суд тога постановил, что публичный API не защищён от использования в рамках "fair use" для целей совместимости ПО. Нам нужна совместимость с Windows - ровно наш случай. Однако же, API-то описывать можно, но только в необходимом объёме, и сам текст заголовочных файлов остаётся авторским произведением. Короче, копировать описание функций можно, копировать заголовки целиком - нельзя. Значит, этим и обойдусь.

Startup code - всё сложнее. Есть как минимум четыре реализации: родная Microsoft, реализация для Wine, для React OS, для MinGW. Ни одну из них лицензия нам не позволяет копировать. Но никто не запрещает их исследовать для обеспечения совместимости в своём софте, чем не брезгуют разработчики сторонних языков. Я язык не разрабатываю, но разрабатываю стандартную библиотеку - могу себе позволить.

Кроме того, могу себе позволить пользоваться любой открытой документацией и сообщениями, в том числе, отчётами об обратном инженеринге.

Сим определён доступный мне инструментарий с позиции закона. Можно преступать к технике.

## It's alive! Alive!

Proof of concept - самое важное в таком деле. Если с доступным инструментарием я могу создать "hello world", значит, могу создать и всё остальное.

И я его [создал](https://gist.github.com/SBKarr/0e0dfc7675d99405ca2a53d24a6b9925). Ушло некоторое время и существенное вложение мозгов, но оно работает. Нет, серьёзно, это кусок кода, который без каких либо заголовков ВООБЩЕ, без библиотек, без SDK порождает приложение для Windows, которое выводит Hello World. Сей факт теперь надёжно закреплён в истории (особенно для юристов, которые за чьи-то деньги могут сомневаться в моей чистоплотности).

Практический смысл простой: даже когда у нас нет вроде бы ничего, на самом деле, у нас есть адрес, который ОС записывает в специальный регистр. Зная то, как уложены данные, мы можем из этого адреса получить доступ к функциям WinAPI и напечатать наш Hello World.

А дальше - дело техники, просто написать код libc, по одной функции за раз. llvm-nm в зубы, чтобы найти, в каком файле что из API ДЕЙСТВИТЕЛЬНО определено, потому как документация в этом нагло врёт.

## ... и когда не сможешь больше ползти - найди того, кто тебя понесёт.

Хороший программист - не тот, кто может написать много кода с нуля, а тот, кто использует для этого чужой код, не создав себе и другим лишних проблем. Писать всю libc, всю математику, работу с памятью, строками - дело неблагодарное и излишнее.

Но в мире уже есть libc, которые не будут меня замыкать в круге GPL. Например, есть пока ещё незрелая llvm libc. А есть вполне зрелая musl libc, вот её-то я и решил воспользоваться. Ведь в libc много функций не зависят от конкретной реализации платформы, и я могу их честно использовать.

Ключевой барьер - куски на ассемблере. Microsoft же всегда решает быть не как все, здесь у них свои Calling conventions. Проблема вполне решаемая - нужно просто аккуратно переписать одни регистры на другие, и проверить. что всё работает. Храни господь авторов llvm (корпорации можешь не хранить, пусть платят, у них денег много) за то, что принесли GAS ASM на Windows.

С malloc та же история, проще всего взять mimalloc от самих же Microsoft для лучшей совместимости.

Что же касается функций платформы, так ведь они уже есть, тот самый слой совместимости с WinAPI, который создавался для кроссплатформы. Его тоже писать заново не надо.

Что остаётся:
* полный startup/termination
* Microsoft C++ ABI
* Управление дескрипторами файлов
* Частичная поддержка локалей

И всё. Это уже готовая libc.

## Заголовки, нейрослопы и галлюцинации

Но всё-таки, что делать с заголовками от WinAPI?

Первоначальная идея была - взять и нагенерировать их нейросетью. Но без ничего нейросеть будет просто копировать то, как оно есть в оригинальном WinAPI, и я нарвусь на правовые проблемы - не годится. Потому, я решил их попросту скопировать из документации, по функции за раз. Когда набралась существенная масса - вот тогда можно подключать нейросеть, чтобы она сформулировала их так, как нужно мне.

Но практика показала досадную штуку: при отсутствии реального Windows SDK в пределах доступности нейронки (да, я действительно честный человек и свято чту закон), она начинает попросту сочинять функции, а не восстанавливать их из своей памяти. Потому, за каждой генерацией я проверял всё вручную через документацию с одной стороны, и через компиляцию уже имеющегося кода, правильно использующего API, с другой.

Помимо прочего, в этом помогали зависимости, и по ходу дела я собрал на своей libc и своих заголовках curl, openssl, freetype и другого по мелочи.

Использовать нейросеть для генерации специфического кода CRT мне тоже показалось таким себе планом, правовой статус копий посредством нейросети не определён, а она ведь возьмёт или из Wine, или из кода самих Microsoft. А отвечать потом мне. Так что здесь ИИ -  не более, чем советчик и интерфейс к поисковику.

## Назад к истокам

Теперь, когда libc у меня есть, можно задуматься о том, как всё-таки с её помощью собирать приложения. Ведь все сборщики, вроде CMake, заточены либо на MinGW, либо на MSVC. То есть, как ни крути, придётся мимикрировать. А, значит, создавать собственные import libs.

И первая ключевая находка - в CMake можно впихнуть любую строку в качестве `CMAKE_MSVC_RUNTIME_LIBRARY`. А потом, для этой строки впихнуть `CMAKE_CXX_COMPILE_OPTIONS_MSVC_RUNTIME_LIBRARY_<MyLibc>`, чтобы передать конкретные флаги компилятору. Например, `--dependent-lib=mylibc`, чтобы использовать мою библиотеку именно как реализацию системных функций.

Зависимости в своих скриптах хотят себе import libs от Windows SDK, коих у меня нет. Но у меня есть список функций, которые должны быть в этих import libs. Значит, я могу написать .def скрипт с ними, а потом из него с помощью llvm-lib собрать их в библиотеки.

И, тем самым, я получаю полный функциональный аналог Windows SDK. Круг замкнулся.

Но зачем столько сложностей, если можно было просто взять и...

Нельзя просто взять. Закон запрещает. Вся эта история ровно о том, как я доказывал закону, что я действительно могу сделать то, о чём заявляю. Законным и доступным мне способом. Если я поступлю иначе - у корпорации тут же возникнет масса вопросов финансового свойства в мой адрес. Только так, с помощью кучи кода и технических решений, я могу выкупить у этих крючкотворцев себе свободу делать то, что хочу я, а не они.

Теперь я могу предельно конкретно ответить юристам, откуда у меня import libs, откуда у меня заголовки, откуда у меня sturtup code, и как я ухитрился всё это получить, не прикасаясь к их неприкосновенным творениям, которыми они диктуют нам свою волю.

Точно также можете ответить и вы, если будете использовать мой код. В конечном счёте, для этого всё и затевалось, из любви к людям и свободе.
