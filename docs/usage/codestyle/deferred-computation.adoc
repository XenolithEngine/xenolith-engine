# Design principle: computation that can be deferred, must be deferred

**The rule**

> If a result is not needed *right now*, do not compute it now. Record that it is
> stale, and compute it once, at the point where someone actually reads it.

This is the single principle behind the largest number of design decisions in the
engine — the dirty-flag pipeline, the lazy caches, the style accessors, the
callback streams. Read it before designing a new subsystem; most of the other
articles are it applied to one area.

**Why it pays here.** A frame touches thousands of nodes at 60–120 Hz, so the
work you avoid is multiplied by the tree size *and* by the frame rate. Deferral
buys three distinct things:

* **Collapsing.** Ten setters called in one frame produce one recomputation, not
  ten. The cost stops scaling with the number of mutations.
* **Elision.** Work whose result is never read costs nothing at all. Most nodes
  never have their inverse transform requested, most style properties are never
  queried, most subtrees have no listener.
* **Ordering.** Computing at the read point means computing with complete inputs.
  An eager setter runs *before* the sibling setter that would have changed the
  answer.

## The five shapes it takes

### 1. Mark dirty, compute in the phase

Geometry setters do not recompute anything; they set a flag and the next visit
runs the matching phase once
([node geometry](scene/node-geometry.adoc), [pipeline](../../design/node-system-event-pipeline.adoc)):

[source,cpp]
----
node->setPosition(...);      // marks transform dirty
node->setContentSize(...);   // marks content size dirty
node->setAnchorPoint(...);   // marks transform dirty
// -> one transform recomputation on the next visit, not three
----

When you change something the engine cannot observe, join the same mechanism
instead of computing eagerly: `markContentSizeDirty()`, `markMeasureDirty()`,
`markLayoutChildrenDirty()`, `markComponentsDirty()`.

### 2. Cache and invalidate

A value that is expensive and re-read often is computed on first read after
invalidation, not on write. `Node` keeps `_transformCacheDirty` and
`_transformInverseDirty` as `mutable` flags: the inverse matrix is produced only
if somebody calls `getParentToNodeTransform()` / `convertToNodeSpace()` — for the
vast majority of nodes it never is.

### 3. Batch at the point of consumption

Children are **not** re-sorted when one is added or reordered; the array is
sorted once before drawing. The header states the rationale plainly:

> Sorts the children array once before drawing, instead of every time when a
> child is added or reordered. This approach can improve the performance
> massively.

The same shape appears in the frame pipeline: allocations go into the frame's own
pool and are released as one block when the frame ends
([memory](core/memory-and-ownership.adoc)) — the per-object free is deferred into a
single pool destruction.

### 4. Lazy accessors — pay per field, not per block

`ui::ResolvedStyle` ([XLUiStyleResolver.h](../../../xenolith/renderer/ui/style/XLUiStyleResolver.h))
returns *raw merged* style data. Nothing is compiled up front:

* `has()` / `getValue()` scan the raw parameter list — no allocation, no pool;
* individual accessors (`fontSize()`, `display()`, `width()`, …) resolve exactly
  one parameter;
* the compiled views (`font()`, `block()`, `background()`, …) expand a whole
  parameter block and are documented as "use only when a consumer genuinely needs
  many fields at once".

A consumer that reads one property pays for one property. Design your own
result types the same way: return the raw material plus accessors, rather than a
fully-expanded struct that most callers will use one field of.

The string equivalent is not materializing at all: a producer takes
`const Callback<void(StringView)> &` so the caller decides whether the bytes ever
become a `String` ([strings](core/strings.adoc)).

### 5. Demand-driven propagation

The strongest form: do not even *dispatch* an event unless somebody subscribed.
Ancestor-component notifications are gated by a per-node counter of listeners in
the subtree ([XLNode.h](../../../xenolith/application/nodes/XLNode.h)):

> Only reaches nodes whose subtree contains a listener (see
> `setWantsAncestorComponents` / `_ancestorComponentsListeners`)

A system that opts into `HandleAncestorComponents` increments the counter up the
chain; a subtree with no listener is skipped entirely, at zero cost. The frame
stack ([systems](scene/node-system-component.adoc)) is the same idea for child events:
the ancestor publishes itself, and descendants deliver *to it* — instead of every
node walking up "just in case".

Lazy construction belongs here too:

| Thing | Created when |
|---|---|
| `CallbackSystem` on a node | the first `set*Callback` is attached |
| worker threads of a `ThreadPool` | the first task is posted (`ThreadPoolFlags::LazyInit`) |
| a thread's `Looper` | `Looper::acquire()` on that thread |
| the thread support pool | first use (documented as "lazy-init and self-contained") |

## Applying it to new code

Before writing a computation, ask in this order:

1. **Does anyone read this?** If the result may go unread, make it an accessor,
   not a stored field.
2. **Can it be recomputed from what I already store?** Then store the inputs and
   a dirty flag, not the result.
3. **Will it be recomputed several times per frame?** Then move it into the phase
   that already runs once per frame, and mark dirty from the setters.
4. **Does it need inputs that are still changing?** Then it *must* be deferred —
   computing in the setter reads a half-updated state.
5. **Am I about to walk the tree to find out whether the work is needed?** Invert
   it: have the interested party register (counter, frame stack), so the
   uninterested case costs nothing.

Common anti-patterns, all seen in review:

* Recomputing a layout inside `setSomething()` instead of marking dirty — the
  caller that sets three properties pays three times, and the first two run on
  inconsistent state.
* Expanding a whole parameter/struct block to read one field.
* Converting a `StringView` to an owned `String` "to be safe" before knowing
  whether it will be stored ([strings](core/strings.adoc)).
* Traversing a subtree every frame to check whether anything changed.
* Constructing a helper object (listener, pool, thread) in a constructor when its
  first use may never come.

## When not to defer

Deferral is not free, and the principle is "computation that *can* be deferred" —
not "everything".

* **Do not defer if the bookkeeping costs more than the work.** A flag plus a
  branch to avoid two multiplications is a loss.
* **Do not defer what makes lifetime unclear.** A lazy value that captures
  pointers into memory that may be gone by the time it is evaluated is a bug, not
  an optimization ([memory](core/memory-and-ownership.adoc), [threads](core/threads-and-dispatch.adoc)).
* **Do not defer error detection.** Validate arguments eagerly and return a
  `Status` ([errors](core/errors-and-status.adoc)); a failure surfacing three phases
  later is much harder to attribute than one returned at the call.
* **Do not defer across a thread hand-off** unless the deferred work is
  self-contained — the reader may be on another thread with another pool.
