# Formatting: what clang-format already decides

**TL;DR**

* [.clang-format](../../../../.clang-format) is authoritative. Do not hand-align
  code — format the file instead.
* Indentation is **tabs**, width 4; continuation lines indent 8. Column limit
  100.
* `*` and `&` bind to the **name** (`Node *node`, `const Mat4 &m`).
* Braces are attached (`if (x) {`); `catch` goes on its own line. Missing braces
  are inserted automatically.
* Includes are **not** sorted and comments are **not** reflowed — those stay
  under your control.
* Comments are short and describe working code: no capital-letter headings, no history of
  fixed bugs — see [Comments](#comments).

## Running it

VSCode formats on save through clangd (see
[.vscode/settings.json](../../../../.vscode/settings.json)). From a shell, use the
SDK toolchain's binary so the version matches the config:

[source,sh]
----
runtime/toolchains/hosts/x86_64-unknown-linux-gnu/bin/clang-format -i <files…>
----

A system `clang-format` usually works too, but an older one may not understand
every option in the file (the config uses recent keys such as
`BreakFunctionDefinitionParameters` and `KeepEmptyLines`) and will warn.

## The settings that actually surprise people

The style is `BasedOnStyle: LLVM` with the deltas below.

[cols="2,3"]
|===
| Setting | Effect

| `UseTab: Always`, `TabWidth: 4`, `IndentWidth: 4`
| Real tab characters for indentation. Do not "fix" tabs to spaces.

| `ContinuationIndentWidth: 8`
| A wrapped expression or parameter list indents by two levels, which is how
wrapped signatures in the codebase look.

| `ColumnLimit: 100`
| Wider than LLVM's 80.

| `PointerAlignment: Right`, `ReferenceAlignment: Right`
| `Node *node`, `const StyleValue &value`.

| `AlignAfterOpenBracket: DontAlign`, `AlignOperands: DontAlign`, `AlignTrailingComments: Never`, `AlignConsecutive*: None`
| No column alignment anywhere. Manually aligned `=` or trailing comments will be
collapsed on the next format — do not create them.

| `BreakBeforeBraces: Custom` with `BeforeCatch: true`
| Attached braces everywhere except `catch`, which starts a new line.

| `InsertBraces: true`
| A brace-less `if`/`for` body gets braces added for you.

| `AllowShortFunctionsOnASingleLine: All`, `AllowShortBlocksOnASingleLine: Always`, `AllowShortLoopsOnASingleLine: true`
| One-line accessors and tiny blocks stay on one line — expected in headers.

| `AllowShortIfStatementsOnASingleLine: Never`
| …but a one-line `if` is always split.

| `NamespaceIndentation: None`, `FixNamespaceComments: true`
| Namespace bodies are not indented; the closing comment is maintained.

| `AccessModifierOffset: -4`, `IndentAccessModifiers: false`
| `public:` / `protected:` sit at the class's own indentation level.

| `SortIncludes: Never`, `IncludeBlocks: Preserve`
| Include order is *yours* and is significant in SCU builds — see
[sources/file-layout.adoc](../sources/file-layout.adoc).

| `ReflowComments: false`
| Comment wrapping is preserved. Keep prose comments inside 100 columns yourself.

| `BreakBeforeBinaryOperators: NonAssignment`, `BreakBeforeTernaryOperators: true`
| A wrapped expression starts the line with the operator.

| `BreakConstructorInitializers: BeforeComma`, `ConstructorInitializerIndentWidth: 0`, `PackConstructorInitializers: NextLine`
| The member-init list style you see in existing constructors.

| `IntegerLiteralSeparator: {Binary: 4, Decimal: 3, Hex: 4}`
| Digit separators are inserted/normalized in numeric literals (`1'000'000`).

| `InsertNewlineAtEOF: true`, `MaxEmptyLinesToKeep: 2`, `KeepEmptyLines.AtStartOfFile: false`
| Trailing newline enforced; at most two blank lines in a row.

| `Standard: c++20`
| The dialect the whole SDK is written in.
|===

## What formatting does not cover

clang-format normalizes layout, not structure. Naming
([sources/naming.adoc](../sources/naming.adoc)), file organization
([sources/file-layout.adoc](../sources/file-layout.adoc)), include order, and comment content
are review concerns, not tool output. A formatted diff is not a reviewed diff.

## Comments

A comment describes the code as it works now: what it does, and the constraint that is not
obvious from reading it. Keep it short — one to three lines is the norm; a longer block is
for a genuinely intricate algorithm or contract, and is still written tersely.

* **No capital-letter headings.** Do not open a comment with a shouted lead-in
  (`/* THE CLIP IS A SYSTEM OF ITS OWN, ...`) and do not stress words in capitals
  (`NOT`, `ONLY`, `EVERY`). Write an ordinary sentence. Acronyms, identifiers and macros
  (`CSS`, `GPU`, `XL_FONT_CACHE_LOG`) are not headings and stay as they are.
* **No history.** How a bug looked, what was measured and reverted, what the code "used to"
  do, which stage introduced it — that belongs in the commit message. If the fix leaves a
  rule the next editor must keep, state the rule in one sentence
  (`// Runs in phase 6: the ancestor's resolver re-resolves this node in phase 4.`).
* **No argument.** Do not justify a design against alternatives nobody wrote or defend it
  in prose; name the reason in a clause and stop.
* Doc comments on public API keep the contract: parameters, return value, ownership,
  threading, units.
