# Drag and drop: `DragSystem`, sources, targets and the payload

**TL;DR**

* One `DragSystem` per scene, on the `SceneContent`. `DragSystem::acquireForNode(node)`
  finds it or installs it — a widget never has to demand that the application
  arranged one first.
* **A drop target registers itself by being drawn.** Add a `DropTarget` system to
  a node; during its owner's visit it publishes its world rect to the nearest
  `DragSystem` above it. So the topmost target receives, and an invisible one
  does not exist.
* **A source is an `InputListener`** — `DragSource` — because the three things a
  source must get right (the threshold, the pointer capture, the abort on exit)
  are all listener-level.
* **The payload is the clipboard's own data model.** `DragData` carries a live
  object for the in-process path *and* a lazy MIME encoder for everything else,
  so a drop target and a paste target are the same handler.
* `DragActions{Copy, Move, Link}`: the source offers a set, the modifier states a
  **preference**, the target has the last word.
* v1 is in-process only. The OS path is not implemented, but nothing in the
  source or target API has to change when it is.

## Making a node draggable

```cpp
node->addSystem(Rc<DragSource>::create([this](DragOffer &offer) {
    offer.local = _item;                       // the live object, for a local drop
    offer.localType = StringView("app/item");  // what a target checks before touching it
    offer.label = _item->getTitle();
    offer.allowedActions = DragActions::Move | DragActions::Copy;
    offer.defaultAction = DragActions::Move;
    offer.decorator = [this] { return makeGhost(); };
    offer.completion = [this](DragActions action) {
        if (action == DragActions::Move) { detach(); }
    };
    return true;   // false refuses: this item is not draggable right now
}));
```

The builder runs once per drag, at the moment the pointer passes the threshold.
Returning `false` is a normal outcome, not an error.

A widget that already owns an `InputListener` — anything derived from
`ui::Button`, for instance — does not need a second one. It can add a swipe
recognizer to its own listener and call `DragSystem::acquireForNode(this)->beginDrag(...)`
directly; that is what `ui::DockTab` does, so that the tap it also handles keeps
working. `DragSource` exists for the widgets that have no listener of their own.

## Making a node a drop target

```cpp
node->addSystem(Rc<DropTarget>::create(DropTargetSlots{
    .accept = [](const DragEvent &e) -> DragResponse {
        if (!e.data->isLocal("app/item")) { return DragResponse(); }
        return DragResponse{e.allowed & DragActions::Move};
    },
    .enter = [this](const DragEvent &) { showHighlight(); },
    .leave = [this](const DragEvent &) { hideHighlight(); },
    .drop  = [this](const DragEvent &e, DragActions) { return take(e.data->getLocal()); },
}));
```

`accept` is a **predicate and must be pure**. It is called during hit testing, for
candidates that may never become the current target, possibly several times in one
frame. All visual feedback belongs in `enter` / `over` / `leave`, which fire only
for the current target.

`enter` and `leave` are an exact bracket on every path out — a drop, a
cancellation, the target leaving the scene mid-drag. A `leave` always precedes the
`drop`, so a highlight is down before the structural change runs.

Returning `DragResponse()` (no accepted action) means *not here*, and the search
continues with whatever is underneath. That is what makes a decorative overlay
transparent to a drag rather than a wall.

## How a target is found

Not by a registry, and not by walking the scene. `DropTarget::handleVisitSelf`
publishes the target and its world rect into the nearest `DragSystem` on the frame
stack, once per frame. Three things follow, and none of them is otherwise cheap to
get right:

* the world rect is the one that was **drawn** — it comes from the visit's own
  transform stack, so there is nothing to re-derive and nothing to fall out of
  sync with;
* registration order is visit order is **paint order**, so the drag walks the
  roster backwards and the first hit is the topmost target;
* a node that is not visited is not registered. Invisible, `display: none`,
  detached — all of them stop being drop targets for free.

The roster is therefore one frame old when a pointer event reads it. That is the
same staleness ordinary input already has: the dispatcher resolves every event
against the previously committed listener storage.

**Do not** hit-test drop targets with `Node::isTouched`: it checks `isVisible()`
rather than the effective visibility, and it redoes a transform the roster already
holds.

## The payload

`DragData` has two ways in, and a target should normally be written against the
second one:

| | `getLocal()` / `isLocal(type)` | `getTypes()` / `preferType()` / `encode()` |
|---|---|---|
| What it is | the live object, by pointer | MIME types and a lazy encoder |
| Cost | nothing | one call to the encoder, per type actually asked for |
| Works for a drag from another process | **no** — it is null | yes |

Listing and matching types never materializes bytes. `encode()` is the only thing
that runs the encoder, and only for a type that was actually offered.

**An encode callback must be thread-agnostic**: capture copies of what it needs,
never capture a scene node, never touch the scene graph. In v1 it happens to run on
the app thread; the contract it is stored under (`sprt::window::ClipboardData`) says
it may run anywhere, and once the OS path exists it will.

The same `DragOffer` describes a payload for the clipboard — and the clipboard has
a description of its own, `ClipboardOffer`, which is the same three fields without
the drag around them (see
[the system clipboard](../window/clipboard.adoc)):

```cpp
app->writeToClipboard(offer.takeClipboardData(this));
```

A copy is written through `ClipboardSession` rather than through `AppThread`
directly; `preferMimeType` lives beside it now, because a paste needed the rule as
much as a drop did.

which is why `ui::TextInput` accepts a dropped payload through exactly the machinery
it pastes with — same type rule (`preferMimeType`, prefix matching, so `text/plain`
selects `text/plain;charset=utf-8`), same caret, same refusal when read-only.

## Actions

The source publishes a mask of what it can do; the modifier picks one of them
(`Ctrl` = Copy, `Shift` = Move, `Ctrl+Shift` = Link, nothing = the source's
default); the target answers with a subset.

**The modifier is a preference, not a demand.** If the target cannot do the
preferred action but can do another one the source offers, that other one happens.
Collapsing the two into a single value is the obvious simplification and it is
wrong: it makes a Copy-only target refuse any drag the user happens to be holding
Shift over. Hence `DragEvent` carries `allowed` and `preferred` as separate fields,
and an `accept` slot is written as `event.allowed & whatICanDo` — never as a bare
constant, or the target claims actions the source never had.

The cursor follows the resolved action (`Copy`/`Move`/`Alias`), becomes `NoDrop`
where nothing is accepted and `Grabbing` where there is no candidate at all.

## Where the cursor comes from

During a drag the pointer is over the **target**, so nothing the source owns can
set the cursor. The `DragSystem` keeps its own `InputListener` on its owner —
disabled when idle, no recognizers, nothing but a window layer — at a deeply
negative priority. Negative-priority listeners land in the dispatcher's post-scene
band, which is walked last, and the window applies the **last** non-`Undefined`
cursor it is handed. So that one window-wide layer outranks every widget under the
pointer, for exactly as long as the drag lasts.

## Lifetime

The source node is routinely destroyed by the very drop that ends the drag — that
is what a move *is*. Two rules make that safe, and both are already in place:

* **`finish()` is a single funnel and runs its body at most once.** Drop, cancel,
  the source leaving the scene, the system leaving the scene — all of them go
  through it.
* **The system detaches the session before finishing it.** Anything that re-enters
  during the drop — a source's `handleExit`, a target's — finds no drag in flight
  and becomes a no-op instead of recursing.

Everything living longer than a frame is held by `Rc`: the source, the target, the
decorator, the data. The roster holds `Rc` too, but is rebuilt every frame and
cannot dangle.

Inside a `drop` slot, **read everything first, then mutate**. The handle you were
given may not resolve afterwards, and the node that delivered the drag may not
exist.

## The decorator

The source supplies a factory; the session owns the node and parks it at
`DragSystem::DecoratorZOrder`, on the **Overlay draw level** — the session calls
`setOverlay(true)` on whatever node it installs. The level is what puts the ghost
above ordinary content and, on the Vulkan path, what draws it after the frame has
been captured; the ZOrder then decides where it sits among the other things on that
level, which is how it stays below `WindowDecorations`. A band of its own, because
`sortAllChildren` is unstable. See
[node-geometry.adoc](node-geometry.adoc) for the level itself.

It is parked under the drag system's owner by default. A decorator that takes its
look from a stylesheet must set `DragOffer::decoratorParent` to a node **inside**
the subtree its `StyleResolver` covers, or it comes out unstyled — a resolver only
ever sees its own subtree.

The decorator must carry no `InputListener`: it would sit between the pointer and
the source that owns the drag.

### A decorator that is not ready yet

`DragOffer::decoratorDeferred` says "build nothing now, I will hand you one":
`beginDrag` creates no node, and the source calls
`DragSession::setDecorator(node)` when it finally has one. Until then nothing
follows the pointer, which for a frame or two reads as the press taking effect
rather than as a missing ghost. A `setDecorator` that arrives after the drop is a
no-op, so a late answer cannot park a node nobody will remove.

It exists for one case: a ghost that shows the *pixels of the thing being dragged*
— see below — has nothing to show until a frame has been rendered, so there is no
node to install yet.

It is **not** what keeps the ghost out of its own cutout. That used to be its
second job, and it was a trap: the pointer sits on the row being copied when the
drag begins, so a ghost built too early was photographed along with it. The
decorator now goes on the Overlay level, which draws after the capture, so the
exclusion holds however and whenever the ghost was made. `XL_DNDTREE_GHOST_NOW=1`
in the dndtree example reproduces the old timing on purpose and must produce a
byte-identical cutout.

## A ghost made of the frame itself

`FrameCapture` (`xenolith/application/resources/XLFrameCapture.h`) copies a
rectangle of what the window last drew into a `Texture`, so a drag ghost can *be*
the row instead of being a second drawing of it:

```cpp
auto capture = static_cast<AppWindow *>(getDirector()->getRenderServer())->getFrameCapture();
if (capture && capture->isAvailable()) {
    auto region = FrameCapture::makeRegion(worldRect,
            getDirector()->getGeneralProjection(), constraints.extent);
    capture->request(region, [source = Rc<DragSource>(source)](FrameCaptureTarget *t) {
        if (auto session = source->getSession()) { session->setDecorator(makeSprite(t)); }
    });
    offer.decoratorDeferred = true;   // see above
}
```

Four things about it are not obvious:

* **One cutout is one image**, sized to the rectangle and written once. There is no
  full-screen history to resize when the window is, and a `Sprite` shows it whole.
* **The region is in surface pixels, y-down.** `FrameCapture::makeRegion` converts
  a world rect through the projection rather than flipping y, because the
  projection is what bakes surface pre-rotation. Size a sprite from
  `getExtent()` divided by `FrameConstraints::density`, not from the rect.
* **Build the world rect with `Node::getWorldBoundingBox()`.** A world origin plus a
  content size is not a world rect: the scene root is scaled by the surface density,
  so the origin is in surface pixels and the size in logical units, and the region
  comes out half-size on every HiDPI surface.
* **A captured frame carries no meaningful alpha.** The compositor was told the
  surface is opaque, so that channel is not a transparency to inherit — draw the
  cutout with `ColorMode(R, G, B, One)` or it blends itself away to nothing.
* **`isAvailable()` is not a formality.** Only the Vulkan backend has a copy path;
  every consumer needs something else to draw, and `XL_NO_FRAME_CAPTURE=1` is how
  that fallback gets exercised on a machine where capturing works.
* **The cutout never contains the Overlay level.** The copy is recorded between the
  content pass and the overlay pass, so anything under a `setOverlay(true)` node —
  the ghost itself, the window decorations — is outside every capture by
  construction, not by timing.

Where the presented image cannot be read (`SwapchainConfig::transferSrc` refused —
Vulkan guarantees only `ColorAttachment` for a swapchain image) the copy instead
rides one extra frame rendered offscreen. That costs a frame and shows a freshly
drawn scene rather than the one on screen; for a ghost that is an improvement,
since such a frame cannot contain the ghost. `XL_NO_SWAPCHAIN_TRANSFER_SRC=1`
forces that route for testing.

## What is not implemented

Only the in-process path. There is no OS-level drag: nothing calls
`wl_data_device.start_drag`, `DoDragDrop` or the XDND protocol, and an incoming
drop from another application is discarded by the backends.

The seams are in place — `DragData` already holds the `ClipboardData` an OS drag
would carry, `DragSession::isExternal()` already exists so a local-only target can
branch on it today, and `DragOffer::externalPolicy` marks where the decision goes.
Two things will genuinely change, and are worth knowing now:

* **"start internally, escalate when the pointer leaves the window" is not
  implementable.** Wayland's `start_drag` needs the serial of a live button press
  and X11 needs a grab taken at press time. The decision has to be made at
  `beginDrag` — which is why `externalPolicy` is on the offer.
* **The decorator stops being a `Node`** for external drags: every OS wants a
  surface or a bitmap. The target API is unaffected; the source API grows one
  optional field.

## Traps

| Trap | What actually happens |
|---|---|
| `acquireForNode` in a constructor or `init()` | a node has no scene until it is added to one, so there is nothing to install the system on. Do it in `handleEnter`, like `FormInputListener` finds its form |
| Side effects in an `accept` slot | it is called during hit testing, for targets that never become current, several times a frame. Feedback belongs in `enter`/`over`/`leave` |
| A source without `setExclusive()` | the dispatcher freezes an event chain's listener set at `Begin` and never re-targets, so the drag stops receiving `Move` the moment the pointer leaves the source. `DragSource` does this for you |
| Accumulating `swipe.delta` | `updateDrag` takes a **position**, in world space and physical pixels. Deltas are not density-divided and a burst of moves in one frame would drift |
| Two overlapping targets at the same `ZOrder` | `sortAllChildren` is unstable, so which one is "topmost" permutes between frames. Give siblings distinct orders |
| A hover highlight written as a `Component` | the components phase re-converges up to 12 times per frame; writing one every frame can thrash it. Change a property on a node the target already owns |
| A stylesheet-styled decorator with no `decoratorParent` | it is parked on the `SceneContent`, outside the `StyleResolver`'s subtree, and renders unstyled |
| A decorator installed without the Overlay level | a bare ZOrder puts it last in the scene but still inside the frame that gets copied out, so a captured ghost photographs itself. `DragSession` sets the level for you; a hand-parked node has to |
| Expecting an overlay node to appear in a cutout | it never can — the copy is recorded between the two passes. Capture the content, not the thing drawn over it |
| A capture region built from `convertToWorldSpace` plus `getContentSize()` | the two are in different spaces once the scene is scaled by the density, so the region is half-size and the ghost shows a corner of the row. Use `Node::getWorldBoundingBox()` |
| Drawing a cutout without `ColorMode(R,G,B,One)` | the presented image's alpha is not a transparency; the ghost blends away to nothing |
| An encode callback capturing `this` of a node | it may run on any thread once the OS path lands. Capture copies |
| Expecting a clipboard round trip to work in a windowed test | taking the OS selection needs an input serial from a focused window. Run those headless, where the controller keeps the data in process |

## Trying it

```sh
XL_FRAME_CAPTURE_TEST=1 ./testapp --headless   # the cutout, and that the Overlay level is not in it
XL_DRAG_BASIC_TEST=1   ./testapp   # roster, bracket, topmost-wins, exactly-once
XL_DRAG_ACTIONS_TEST=1 ./testapp   # modifiers, negotiation, cursor
XL_DRAG_TEXT_TEST=1    ./testapp   # a text field receiving a drop
XL_DRAG_PAYLOAD_TEST=1 ./testapp --headless   # lazy encoding + clipboard round trip
```

`drag-actions` also registers `drag-actions.points` and `drag-actions.state` for
the `SceneInspector`, so a synthetic pointer drag can be driven and read back step
by step — the only way to exercise the threshold and the pointer capture, which the
API-driven phases bypass.
