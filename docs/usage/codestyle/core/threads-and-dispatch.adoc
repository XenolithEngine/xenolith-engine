# Threads and `sprt::dispatch`: loopers, tasks, handles

**TL;DR**

* Threads are not created ad hoc. Work is posted to an existing **`Looper`** —
  one per thread, obtained with `Looper::acquire()`.
* Post to a specific thread with `performOnThread(...)`; offload CPU work to the
  worker pool with `performAsync(...)`. Both take a `Ref *` that keeps the
  callback's owner alive.
* Every async operation (timer, file, socket, process, watch) returns an
  `Rc<Handle>`. **Keep it** — dropping it is how you cancel, and losing it means
  you can no longer stop the operation.
* Callbacks from a `Looper` always run **on that looper's thread**. That is the
  whole thread-affinity story: no locks needed for data owned by that thread.
* Never block a looper thread. No sleeping, no synchronous I/O, no waiting on
  another thread's result.
* A thread's own pool memory stays on that thread — copy it out before handing it
  over. To move a whole dataset, use an **independent pool**
  (`Rc<PoolRef>` / `Rc<SharedRef<T>>`) and transfer ownership of it
  ([memory](../core/memory-and-ownership.adoc)).

## The thread map of an application

| Thread | Looper name | What lives there |
|---|---|---|
| main / context | `Main` | `Context`, `ContextController`, the OS window and its events |
| application | `App` | `AppThread`, `Director`, the scene graph, all `Node`s, UI callbacks |
| gAPI loop | — (owns a `Looper`) | `core::Loop` — frame scheduling, GPU submission |
| worker pool | — | short CPU tasks posted with `performAsync` |

`AppThread` ([XLAppThread.h](../../../../xenolith/application/XLAppThread.h)) and
`Context` ([XLContext.cc](../../../../xenolith/application/XLContext.cc)) each
acquire their own looper at `threadInit()`:

[source,cpp]
----
_appLooper = sprt::dispatch::Looper::acquire(sprt::dispatch::LooperInfo{
	.name = StringView("App"),
	.workersCount = getContextInfo()->appThreadsCount,
	.engineMask = sprt::dispatch::QueueEngine::Any & ~sprt::dispatch::QueueEngine::ALooper});
----

**Scene-graph code runs on the app thread.** A `Node`, a `System`, a `Component`
and everything they own are single-threaded by construction — that is why none of
them take locks. Touching a node from any other thread is a bug, not a race to be
fixed with a mutex.

## `Looper`

[looper.h](../../../../runtime/include/sprt/runtime/dispatch/looper.h). One per
thread, and that is enforced: `acquire()` returns the thread's looper, creating it
on the first call (the `LooperInfo` is used only then); `getIfExists()` returns
`nullptr` if the thread has none.

Driving it: `run(timeout, wakeupInfo)` (until timeout or `wakeup()`), `poll()`
(non-blocking), `wait(timeout)`. Application code rarely calls these — the app and
context threads already run their loop.

The backend is chosen per platform from `QueueEngine`
([queue.h](../../../../runtime/include/sprt/runtime/dispatch/queue.h)): `URing`,
`EPoll`, `ALooper`, `IOCP`, `KQueue`, `RunLoop`, `Wasm`. Mask it in `LooperInfo`
only to *exclude* a backend for a documented reason — as `AppThread` excludes
`ALooper` because it cannot be stopped gracefully.

## Getting work onto a thread

[source,cpp]
----
// run on the looper's thread; from another thread this queues
looper->performOnThread([this] { … }, this, false, "MyTag");

// ... immediate = true additionally means "if already on this thread, run in place"
looper->performOnThread([this] { … }, this, true);

// CPU work on the worker pool
looper->performAsync([] { … }, ref);

// xenolith wrappers with the same shape
context->performOnThread([] { … }, ref);
appThread->performOnAppThread([] { … }, ref);
----

Two things to get right:

* **The `Ref *` argument is a lifetime guarantee, not decoration.** It is retained
  until the callback has run, which is what makes `[this]` safe in a queued
  callback. Omit it and a destroyed owner is called back.
* **`immediate` is not "run now".** Without it the work is queued even when you
  are already on the target thread — it runs on the next loop iteration. With it,
  an on-thread call runs in place, re-entering your own call stack. Default to
  `false`; use `true` only when the caller genuinely tolerates re-entrancy.

Check affinity with `looper->isOnThisThread()` (`Loop::isOnThisThread()` on the
gAPI side) when a function must behave differently depending on where it was
called from.

## Handles

Every asynchronous operation returns an `Rc<Handle>` subclass —
`TimerHandle`, `PollHandle`, `FileHandle`, `WatchHandle`, `ListenHandle`,
`StreamHandle`, `ProcessHandle`
([handle.h](../../../../runtime/include/sprt/runtime/dispatch/handle.h)):

[source,cpp]
----
// xenolith/renderer/ui/style/XLUiStyleSystem.cc
auto handle = looper->watchFile(StringView(real),
		WatchFlags::Modified | WatchFlags::MovedTo | WatchFlags::Created,
		[this](WatchFlags) -> Status {
	rebuildFromSources();      // runs on the looper's thread
	return Status::Ok;         // anything else cancels the watch
}, this);
if (handle) {
	_watches.emplace_back(sp::move(handle));   // keep it, or you cannot cancel
}
----

Rules:

* **Store the handle** for anything that stays armed (timers, watches, listeners).
  A member `Rc<…Handle>` (or a vector of them) is the normal shape; cancel in the
  owner's teardown.
* **A null return means "unsupported here"**, not "failed" — `watchFile` and
  `listenSocket` return `nullptr` on backends without an implementation. Check it.
* `cancel()` is asynchronous and its `Status` says what happened
  (`ErrorAlreadyPerformed` when the handle was not running, `ErrorNotPermitted`
  when only the queue can stop it, …). `pause()`/`resume()` work only when
  `isResumable()`.
* Completion callbacks receive a `Status` and run on the looper's thread.

What the looper can do for you without spawning a thread: `scheduleTimer` /
`schedule`, `readFile` / `writeFile`, `watchFile`, `listenSocket` /
`connectSocket`, `spawnProcess`, `listenPollableHandle` for a raw fd. Reach for
these before reaching for a thread.

## `Task`: three phases, two threads

[task.h](../../../../runtime/include/sprt/runtime/dispatch/task.h). A `Task` splits
work by *where it runs*:

| Callback | Thread |
|---|---|
| `PrepareCallback` | the issuer's thread, before queueing |
| `ExecuteCallback` | a worker thread |
| `CompleteCallback` | the dispatcher (originating) thread, after execution |

So the pattern "compute off-thread, apply on the owning thread" needs no manual
hand-off: put the computation in `execute` and the mutation in `complete`. The
`bool` returned by `execute` becomes the success flag passed to `complete`.
`addRef()` keeps objects alive for the whole task, and a `TaskGroup` counts
completions when you fan out.

A task with only a complete callback is the idiomatic "call me back on this
thread" object.

## Threads you own, and the pool

`Thread` ([thread.h](../../../../runtime/include/sprt/runtime/dispatch/thread.h)) is
the base for a long-lived thread with its own loop — `AppThread` is one. Override
`threadInit()` / `worker()` / `threadDispose()`; `run()` starts it, `stop()` +
`waitStopped()` ends it. `wrap()` adopts the calling thread instead of spawning.
`Thread::getCurrentThread()` and `findSpecificThread<T>()` (which walks the parent
chain) identify where you are.

`ThreadPool`
([thread_pool.h](../../../../runtime/include/sprt/runtime/dispatch/thread_pool.h)) is
the shared worker pool behind `performAsync`; `ThreadPoolFlags::LazyInit` means no
threads are spawned until the first task. Do not create your own pool for
occasional work — use the looper's.

## `Bus`: events across threads

[bus.h](../../../../runtime/include/sprt/runtime/dispatch/bus.h) delivers a
`BusEvent` to `BusDelegate`s subscribed by category. Each delegate carries the
`Looper` it wants to be called on, so `Bus::dispatchEvent()` from any thread
results in the callback running on the delegate's own thread. Call
`invalidate()` when the owner goes away.

## Memory across threads

Each thread owns its pools: `thread_info::threadPool` lives as long as the thread,
and `workerPool` is a child that is cleared around each unit of work
([thread_info.h](../../../../runtime/include/sprt/runtime/dispatch/thread_info.h)).
`Looper::getThreadMemPool()` exposes the thread's pool.

Therefore:

* **Data in a thread's own pool belongs to that thread.** Passing a
  `mem_pool::String`, a pool container or a `StringView` into that memory to
  another thread is a dangling read the moment the pool is cleared. Materialize
  into malloc-backed storage (`mem_std::`) — or copy into the *target* thread's
  pool once you are there ([strings](../core/strings.adoc)).
* Captures in a lambda posted to another thread follow the same rule; `Rc<T>`
  captures are fine (they are heap objects with their own refcount), views into
  the sending thread's pool are not.
* **The supported way to move a whole dataset** is an independent pool — one with
  its own internal allocator, or one over an external `allocator_t` carried
  alongside — packaged as `Rc<PoolRef>` or `Rc<SharedRef<T>>`. Allocators are
  thread-safe and may be transferred freely; allocating *from a pool* is not, so
  this is a hand-off of ownership, not shared access. See
  [05 § Independent pools](../core/memory-and-ownership.adoc). The frame pipeline
  (`FrameRequest` / `FrameQueue` / `CommandList`) and `dispatch::Queue` are built
  this way.
