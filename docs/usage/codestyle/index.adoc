# Code style reference

The conventions that make code in this monorepo look and behave like the code
around it. Each topic is a standalone article: a TL;DR block for a quick check,
then the rule with its rationale and real examples from the tree.

Articles are grouped by what you are about to touch — one directory per group:

    deferred-computation.adoc   the design principle everything below is an instance of
    sources/                    how a source file looks: units, layout, naming, formatting
    platform/                   what differs per platform: guards, and the runtime as a libc
    core/                       the runtime primitives: memory, strings, errors, threads, data
    scene/                      the scene graph: node geometry, systems and components
    ui/                         the widget kit: forms, fields and focus
    window/                     windows, subwindows and OS dialogs

[deferred-computation.adoc](deferred-computation.adoc) is different in kind: it
states the **design principle** the engine is built on — *computation that can be
deferred, must be deferred* — which is what most of the mechanisms in the other
articles are instances of. Read it first.

This reference is also the source for the `code-style` agent skill
([.claude/skills/code-style/SKILL.md](../../../.claude/skills/code-style/SKILL.md)) —
the skill routes to these files rather than duplicating them, so an edit here
reaches both the humans and the tooling.

Build and verification live elsewhere: see [AGENTS.md](../../../AGENTS.md) and
[makefiles.adoc](../makefiles.adoc). To decide **which node processing phase**
(and therefore which `SystemFlags` bit and which `handle*` hook) a behaviour
belongs in, the authority is
[design/node-system-event-pipeline.adoc](../../design/node-system-event-pipeline.adoc);
the `scene/` articles route to it rather than restating it.
